## 개요

Liner API는 검색과 답변 생성을 제공하는 7종의 HTTP API입니다. 이 문서는 공식 문서와 실제 호출 결과를 대조해 작성했으며, 문서 기재 사항과 실제 동작이 다른 항목은 실측을 기준으로 기술합니다.

### API 목록

| API | 기능 | 1회 단가 |
|---|---|---|
| **Web Search** | 웹 검색 결과 목록 반환. 답변 생성 없음 | $0.001 |
| **Scholar Search** | 논문 검색. 요청 형식은 Web Search와 동일하나 별도 코퍼스를 조회 | $0.0003 |
| **Quick Answer** | 검색 1회 후 답변 생성 | $0.003 |
| **Search Agent** | 질의를 검색어로 재작성해 다중 검색 후 인용이 포함된 답변 생성 | $0.02 |
| **Deep Research** | 다중 라운드 검색 후 목차 구조의 리포트 생성. 출처 100건 이상 수집 | $0.2 |
| **Visualization** | 질의에 대응하는 단일 HTML 문서 생성. 화면 유형은 서버가 선택 | $0.01 |
| **Visual Answer** | 검색·산문 답변·시각화를 결합. 질의 유형에 따라 3개 경로로 분기 | $0.15 |

최저 단가와 최고 단가의 차이는 667배입니다.

## 0. 용어 사전

이 문서에서 사용하는 용어입니다.

| 용어 | 뜻 |
|---|---|
| **엔드포인트** | 호출할 주소. `POST /api/v1/agents/search` 같은 것 |
| **도구(Tools)** | 시킨 것 하나만 하고 끝나는 API. 검색만 하고 답은 안 만듦 |
| **에이전트(Agent)** | 여러 단계를 알아서 밟는 API. 검색하고 읽고 답까지 씀 |
| **스트리밍** | 답이 다 완성될 때까지 기다리지 않고 글자가 만들어지는 대로 조금씩 받는 것. ChatGPT에서 타자 치듯 글자가 나오는 그 방식 |
| **SSE** | Server-Sent Events. 스트리밍을 구현하는 HTTP 방식의 이름. 서버가 연결을 안 끊고 조각을 계속 밀어 보냄 |
| **이벤트** | SSE로 오는 조각 하나. `type` 필드가 붙어서 "이건 출처 목록", "이건 답변 글자"를 구분함 |
| **QPS** | Queries Per Second. 초당 보낼 수 있는 요청 수 |
| **그라운딩** | 모델이 기억에서 지어내지 않고 실제로 검색해 온 문서에 근거해 답을 만드는 것 |
| **인용 매핑** | 답변의 어느 문장이 어느 출처에서 나왔는지 짝지어 주는 데이터 |
| **캐시 키** | 저장해 둔 결과에 붙이는 이름표. 나중에 같은 검색인지 알아보려고 씀 |
| **TTL** | 캐시를 언제 버릴지 정하는 유효 기간 |
| **페이지네이션** | 결과를 여러 페이지로 나눠 받는 것. "다음 10개" 같은 기능 |
| **DOI** | 논문에 붙는 영구 식별자. `10.48550/arxiv.2408.08921` 같은 형태 |
| **SJR** | SCImago Journal Rank. 학술지 등급 지표. Q1이 최상위 |
| **쿼리 재작성** | 사용자 질문을 검색 엔진에 잘 걸리는 검색어로 바꾸는 것 |
| **쿼리 분해** | 하나의 질문을 여러 검색어로 나눠 던지는 것 |
| **과제 분해** | 하나의 질문을 여러 개의 독립된 조사 항목으로 쪼개는 것. **Liner는 이걸 하지 않습니다** (11회 연속 과제 1개 실측) |
| **atlas** | Liner 시각화 엔진의 내부 코드명. `gemini-3-flash-preview` 모델로 구동됨이 응답에서 확인됨 |
| **테마(theme)** | atlas가 질의를 보고 자동으로 고르는 화면 종류. comparison, hierarchy 등 10종 |
| **라우터** | 에이전트가 질의를 어떤 경로로 처리할지 정하는 내부 판단. `data-search-decision` 이벤트로 노출됨 |

## 1. 전체 지도

Liner API는 두 계층으로 나뉩니다.

| 계층 | 포함 | 성격 |
|---|---|---|
| **Tools API** | Search API (web / scholar), Visualization API | 원재료만 줌. 답변 생성 없음 |
| **Agent API** | Quick Answer, Search, Deep Research, Visual Answer | 검색부터 답변 작성까지 한 번에 |
| **부가** | Liner MCP, Credits Balance | 통합 수단, 잔액 조회 |

"6종 API"로 광고하지만 실제 엔드포인트는 7개입니다. Search API가 web/scholar 둘로 나뉘고, Visualization은 엔드포인트 하나에 파라미터로 두 모드를 구분하면서 단가는 따로 매깁니다.

### 가격과 처리량 한눈에

| API | 1,000회 | 1회 | QPS | 스트리밍 | MCP |
|---|---|---|---|---|---|
| Scholar Search | $0.3 | $0.0003 | 2 | 없음 | 제공 |
| Web Search | $1 | $0.001 | **제한 없음** | 없음 | 제공 |
| Quick Answer Agent | $3 | $0.003 | **제한 없음** | SSE | 제공 |
| Visualization | $10 | $0.01 | 2 | SSE | 미제공 |
| Search Agent | $20 | $0.02 | 2 | SSE | 제공 |
| Web Search + Visualization | $20 | $0.02 | 2 | SSE | 미제공 |
| Visual Answer Agent | $150 | $0.15 | 2 | SSE | 미제공 |
| Deep Research Agent | $200 | $0.2 | 2 | SSE | 제공 |

최저가와 최고가의 차이가 **667배**입니다. 어느 API를 고르느냐가 곧 비용 구조를 결정합니다.

"QPS 제한 없음"에는 "공정 사용 정책 적용"이라는 단서가 붙습니다. 숫자로 된 상한은 문서에 없습니다.

## 2. 모든 API에 공통되는 사항

### 접속

```
Base URL : https://platform.liner.com/api/v1
인증     : x-api-key: <YOUR_API_KEY>       ← Bearer 토큰이 아님
```

MCP만 예외적으로 Bearer 토큰과 OAuth 2.1을 씁니다.

### 실제 요청 헤더 (플레이그라운드에서 확인)

```
POST /api/v1/agents/quick-answer HTTP/1.1
Host           platform.liner.com
Content-Type   application/json
Accept         text/event-stream        ← SSE 스트림
x-api-key      $LINER_API_KEY
```

`Accept: text/event-stream`은 문서상 Deep Research에만 필수라고 적혀 있는데, **실제로는 Quick Answer도 이 헤더를 보냅니다.**

### 응답 방식

- Agent API와 Visualization API는 기본이 SSE 스트리밍
- `stream: false`를 주면 완성된 JSON 하나로 받음
- Search API는 스트리밍 미지원. 일반 JSON만

`stream: false`로 받으면 이 모양입니다.

```json
{
  "answer": "최종 답변 전문",
  "references": [ { "title": "...", "url": "...", "hostname": "...", "date": "" } ],
  "chunks": [ ]
}
```

`chunks`는 **잡동사니 서랍**입니다. 답변과 출처를 뺀 나머지 이벤트가 전부 여기 몰립니다.

### 요청 본문 형식

Content-Type 드롭다운에 일곱 가지가 보이지만 안내 문구가 답입니다.

> "Liner API only accepts JSON bodies, but other formats are shown for reference."

**JSON만 실제로 동작합니다.** 나머지는 참고용 미리보기입니다.

### 에러

| 상태 | 코드 | 재시도 | 의미 |
|---|---|---|---|
| 400 | `INVALID_REQUEST` | 불가 | 본문 형식 오류, 필수 필드 누락 |
| 401 | `UNAUTHORIZED` | 불가 | API 키 누락·무효 |
| 402 | `INSUFFICIENT_CREDITS` | 불가 | 크레딧 부족 |
| 429 | `RATE_LIMITED` | 가능 | `Retry-After` 준수 (최소 1초) |
| 500 | `INTERNAL_ERROR` | 가능 | 백오프 후 재시도 |
| 502 | `DOWNSTREAM_ERROR` | 조건부 | 본문의 `retryable` 필드로 판단 (최소 5초) |

**HTTP 상태 코드가 아니라 응답 본문의 `retryable` 불리언을 보고 재시도를 결정하라고 문서가 명시합니다.**

스트리밍 중에는 헤더를 바꿀 수 없으므로, 오류가 HTTP 상태가 아니라 `data-error` 이벤트(id는 `data-error-1` 고정)로 옵니다. 이벤트가 오면 스트림이 종료됩니다.

### 레이트 리밋

- 1초 고정 윈도우
- **남은 호출량이 다음 초로 이월되지 않음**
- `X-RateLimit-*` 계열 헤더의 존재 여부는 문서에 없음

### 과금

- 선불 크레딧 차감, 최소 결제 금액 없음
- **성공한 호출 단위**로 과금
- 크레딧 잔액은 백만분의 1달러 단위 정수 (`12500000` = $12.50)
- 정책 위반 응답은 과금하지 않음 (Visual Answer 문서에 명시)

### 무료 체험

플레이그라운드 상단에 이렇게 뜹니다.

```
Test all APIs for free  |  5 requests left for this API
```

- **API마다 각각 5회씩**입니다. Quick Answer 5회, Search API 5회, Deep Research 5회가 따로
- **로그인 없이도 됩니다.** 기기 식별자로 세는 것으로 보임
- 가입 시 **최대 $15 크레딧** 제공

$15면 이 정도입니다.

| API | 가능 횟수 |
|---|---|
| Scholar Search | 50,000회 |
| Web Search | 15,000회 |
| Quick Answer | 5,000회 |
| Deep Research | 75회 |

## 3. Tools API

### 3-1. Search API — Web Search

> **한 줄로**
> 구글 검색을 사람 대신 코드가 하는 API. 검색 결과 목록만 JSON으로 주고, 답변은 안 만들어 준다.

답변을 붙일 대상이 없습니다. **검색 결과 목록 자체가 응답 전부**입니다. 검색창에 단어 넣고 엔터 친 결과 화면을 JSON으로 받는 것이라고 보면 됩니다.

**엔드포인트**: `POST /api/v1/tools/search/web`

**입력**

| 필드 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `query` | string | 필수 | 검색어 |
| `country_code` | string | 선택 | 국가. 예시 값 `"us"`. **무엇이 바뀌는지 설명 문장은 문서에 없음** |
| `lang` | string | 선택 | 언어. 예시 값 `"en"` |
| `date_range` | string | 선택 | `past_day` / `past_week` / `past_month` / `past_year` |
| `max_results` | integer | 선택 | 1~20, 기본값 10 |

`country_code`와 `lang`이 **별개 파라미터**입니다. 하나로 합치지 않았다는 건 서로 다른 축이라는 뜻입니다. "한국이지만 영어 문서" 같은 조합이 가능한 구조입니다.

**출력**

```json
{
  "requestId": "req_abc123",
  "results": [
    {
      "title": "EU AI Act Implementation Timeline",
      "url": "https://example.com/eu-ai-act",
      "hostname": "example.com",
      "faviconUrl": "https://example.com/favicon.ico",
      "description": "The European Union's AI Act enters into force, introducing...",
      "date": "2026-04-15"
    }
  ],
  "totalCount": 10
}
```

`answer` 같은 필드가 아예 없습니다. `description`도 Liner가 요약해 준 게 아니라 그 페이지에서 잘라낸 발췌문입니다. 예시에서도 `introducing...`으로 끝이 잘려 있습니다.

**단가**: 1,000회당 $1 / QPS 제한 없음

#### 문서가 권장하는 캐싱

> "`(query, country_code, lang, date_range)` 단위로 결과를 캐싱해 비용을 줄일 수 있습니다. 뉴스성 페이지는 시간 단위로, 상시 콘텐츠는 일 단위로 갱신하는 것을 권장합니다."

성공한 호출 1건당 과금이므로, 같은 질의를 100번 던지면 같은 결과를 받으면서 100번 결제됩니다.

**캐시 키가 네 값의 조합인 이유**: `date_range` 하나만 달라도 결과가 달라지므로 다른 항목으로 저장해야 합니다. `query`만 키로 쓰면 지난주 결과를 전체 기간 결과인 양 잘못 꺼내 씁니다.

**갱신 주기가 갈리는 이유**

| 성격 | 예 | 결과가 바뀌는 속도 | 권장 주기 |
|---|---|---|---|
| 뉴스성 | "오늘 환율" | 몇 시간 만에 새 기사가 상위로 | 시간 단위 |
| 상시 콘텐츠 | "데드락이란" | 몇 달이 지나도 상위 결과가 그대로 | 일 단위 |

#### 실측 결과 — "machine learning" (영어)

출처 10개가 이렇게 나왔습니다.

```
Microsoft Learn · GeeksforGeeks · Google for Developers · MIT Open Learning
IBM · Coralogix(블로그) · Coursera · YouTube · 위키백과 · STL Tech(블로그)
```

**위키백과, IBM, MIT, 구글 공식 문서가 들어 있습니다.** 권위 있는 정의 출처를 잘 물어옵니다.

확인된 사실:

| 항목 | 실측 |
|---|---|
| `description` 평균 길이 | **약 130자.** 한 문장, 대부분 `...`으로 잘림 |
| `date` | **10건 중 7건이 `null`** |
| `faviconUrl` | `https://www.google.com/s2/favicons?domain=…&sz=128` |
| `totalCount` | 반환된 개수 (전체 검색 결과 수가 아님) |

**쓰레기가 섞입니다.** YouTube 결과의 `description`이 이랬습니다.

```
"Comments ; All Machine Learning algorithms explained in 17 min · Fundraiser. 2.1M views"
```

영상 페이지의 댓글 영역 텍스트가 그대로 들어왔습니다. 출처마다 정보 품질이 고르지 않으므로 앱 쪽에서 대처가 필요합니다 — 예컨대 `hostname`이 `youtube.com`이면 `description`을 본문 요약으로 신뢰하지 않는 식입니다.

**`faviconUrl`은 구글 서비스입니다.** 이 URL을 화면에 그대로 `<img src>`로 박으면 사용자가 어떤 출처를 보는지가 구글로 전송됩니다. `hostname`으로 아이콘을 직접 정하거나 한 번 받아서 로컬에 캐시하는 편이 낫습니다.

#### 추가 실측 (4회 · 2026-08-24)

**검색어 언어가 결과 언어를 결정합니다.** `GraphRAG`(영어)는 10건 전부 영어 문서, `그래프래그`(한국어)는 10건 전부 한국어 문서가 왔습니다. IBM 같은 다국어 사이트는 각각 해당 언어판 페이지가 잡혔습니다. `lang` 파라미터 없이도 검색어 자체가 스위치 역할을 합니다.

**쿼리 재작성을 하지 않습니다.** `onthology`(오타)를 그대로 검색해 정타 `ontology` 문서 대신 그 오타가 실제로 들어 있는 하이데거 존재론 철학 논문이 나왔습니다. 에이전트 계열과 달리 **Tools는 던진 문자열 그대로 매칭합니다.** 오타 교정·동의어 확장은 우리 몫입니다.

**`date_range: "past_day"`는 검색을 망가뜨립니다.** 최근 24시간 내 갱신된 페이지를 우선하다 보니, 개념 질의에 아파트 분양 공고·네이버 금융 시세·나무위키 잡문서가 6건 중 4건을 차지했습니다. 상시 개념 검색에는 `date_range`를 쓰지 않는 것이 맞습니다.

**`date`는 발행일이 아니라 최종 수정일입니다.** 수년 된 나무위키 문서와 네이버 금융 페이지가 `"2026-08-23"`(호출 전날)으로 왔습니다. 최신성 판단에 이 필드를 쓰면 자주 고쳐지는 페이지가 항상 최신으로 둔갑합니다.

**`totalCount`가 `max_results`보다 작을 수 있습니다.** `max_results: 10`인데 `totalCount: 6`이 왔습니다. 결과가 부족하면 채우지 않고 그만큼만 줍니다.

**한계**

- 한 번에 최대 20건. **페이지네이션 파라미터가 문서에 없음**
- 답변 합성과 인용 매핑은 직접 구현해야 함

### 3-2. Search API — Scholar Search

> **한 줄로**
> 논문만 검색하는 API. 웹 검색이랑 검색창은 똑같이 생겼는데 다른 서가에서 꺼내 온다.

**웹 검색에 필드 세 개를 덧붙인 게 아니라, 아예 다른 것을 검색합니다.** 요청 형식이 같고 응답 필드가 포함 관계라서 비슷해 보일 뿐입니다.

**엔드포인트**: `POST /api/v1/tools/search/scholar`

**입력**: Web Search와 동일. 단 `country_code`를 지원하지 않습니다.
> 문서 원문: "Web과 동일하나 `country_code`는 지원하지 않습니다"

**출력**: Web Search의 모든 필드에 세 가지가 더해집니다 — `citationCount`(인용 수), `authors`(저자 목록), `journal`(게재 저널).

**단가**: 1,000회당 $0.3 / 2 QPS. **전체 API 중 최저가**입니다.

#### 실측 결과 ① — 한국어 "기계학습"

출처가 전부 국내 학술 DB였습니다.

```
DBpia · earticle · kiss.kstudy · papersearch · 교보문고 · 한국보건사회연구원
```

**문제는 나온 논문의 성격입니다.**

- 광역자치단체의 기계학습 행정서비스 업무유형 연구
- 회계이익예측을 위한 기계학습 성과 비교
- 기계학습 방법을 이용한 치매진단 모델 연구

전부 "기계학습을 어디에 갖다 썼다"는 응용 논문입니다. **기계학습이 무엇인지 정의하는 문헌은 한 편도 없었습니다.**

피인용 수는 이랬습니다.

```
2, 1, 0, 0, 1, 0, 0, 0, 0, 0     →  합계 4
```

#### 실측 결과 ② — 영어 "machine learning"

```
15, 6, 0, 1, 1, 4, 3, 12, 0, 0   →  합계 42, 최댓값 15
```

10배 늘었지만 **여전히 신뢰도 신호로 쓸 수 없는 수준**입니다. 이 분야 정본 교재는 인용 수가 만 단위인데 그런 문헌이 목록에 하나도 없었습니다.

대신 올라온 것들:

- IGI Global 편집서 챕터 4건
- IJRASET 게재 논문 (초록이 같은 말을 반복하는 저품질 문서)
- CiteSeerX 발표 슬라이드 (같은 문장이 네 번 반복)

#### 랭킹이 제목 일치 기준으로 보입니다

영어 결과 **10건 중 6건의 제목이 정확히 "Machine Learning"**이었습니다. 한국어 결과도 전부 제목에 "기계학습"이 들어 있었습니다.

**영향력이 아니라 제목 일치를 기준으로 정렬되는 것으로 보입니다.** 정본 문헌이 안 나오는 이유가 이걸로 설명됩니다.

#### Web Search와의 결정적 차이 — 발췌문 길이

같은 쿼리 "machine learning"에 대한 `description` 길이입니다.

| | Web Search | Scholar Search |
|---|---|---|
| 평균 길이 | 약 130자 | **약 950자** |
| 최장 | 155자 (위키백과) | **1,900자** (IJRASET) |
| 형태 | 한 문장, 대부분 `...`으로 잘림 | **초록 전문** |

**Scholar는 초록이 통째로 옵니다.**

다만 항상은 아닙니다. 한국보건사회연구원 결과는 초록이 아니라 **목차**가 들어와 있었습니다.

#### 여기서 주의할 결론

발췌문이 길다고 근거가 좋은 게 아닙니다.

```
Web     : 권위 있는 출처(위키백과·IBM·MIT)의 짧은 정의문
Scholar : 저품질 출처(IGI Global 챕터 등)의 긴 초록
```

**키워드 질의 기준으로는, 개념의 정의를 얻는 용도에 Web 쪽 출처가 나았습니다.** 서로 다른 권위 출처 여러 곳이 같은 정의를 말하는 것이 초록 한 편보다 강한 근거이기 때문입니다.

단, 이 실측은 두 API에 **키워드만** 던진 결과입니다("기계학습" 같은 명사 하나). "기계학습의 정의는 무엇인가"처럼 질문 형태로 던지면 Scholar가 다른 성격의 논문(서베이·교과서형)을 가져올 가능성은 검증하지 않았습니다. 질의 형태를 바꾼 비교 실험 전에는 이 우열을 일반 결론으로 확정하지 마십시오.

#### 코드 짤 때 걸릴 것

세 필드가 모두 비어 있을 수 있습니다.

```typescript
interface ScholarResult {
  title: string;
  url: string;                    // hostname === "doi.org" 이면 경로가 DOI
  hostname: string;
  faviconUrl: string;             // 구글 서비스 URL
  description: string;            // 초록인 경우가 많으나 목차·슬라이드일 수도
  date: string;                   // "2023-03-23" | "2016" | ""  ← 세 형태 모두 실측
  citationCount: number;
  authors: string[] | null;
  journal: string | null;         // 학술지명이 아님 (아래 참고)
}
```

**`journal` 필드가 학술지명이 아닙니다.** 실측된 값들입니다.

```
"RePEc: Research Papers in Economics"                    ← 경제학 아카이브
"Apress eBooks"                                          ← 출판사 전자책 플랫폼
"Zenodo (CERN European Organization for Nuclear Research)" ← 리포지터리
"Advances in computer and electrical engineering book series" ← 총서
```

화면에 "게재지"라고 표시하면 `Zenodo (CERN…)` 같은 값이 그대로 나갑니다.

**DOI는 별도 필드가 아니라 `url`에 들어 있습니다.**

```
https://doi.org/10.1201/9781003290100
https://doi.org/10.22214/ijraset.2023.55224
```

10건 중 6건이 `hostname: "doi.org"`이고 경로가 곧 DOI입니다.

**URL이 정규화되어 있지 않습니다.** 같은 DBpia인데 형태가 제각각이었습니다.

```
https://www.dbpia.co.kr/journal/articleDetail?nodeId=NODE07026298
http://www.dbpia.co.kr/Journal/ArticleDetail/NODE06680416?q=(%5B%EA%B8%B0...
```

http/https가 섞이고, 경로 대소문자가 다르고, 검색 파라미터가 붙어 있습니다.

책임을 분명히 하면, 이것은 **Liner 쪽에서 고쳐야 할 결함**입니다. 다만 고쳐지기 전까지는 우리 코드가 URL 문자열을 문서의 식별자로 쓰는 순간 같은 논문을 서로 다른 출처로 세게 되므로(출처 중복 제거, "여러 출처가 같은 정의를 말한다" 식의 근거 집계가 전부 부풀려짐), 방어는 우리 몫입니다.

#### 추가 실측 (2회 · 2026-08-24)

**한국어 논문의 `citationCount`는 전부 `0`입니다.** `null`이 아니라 정수 0이라서, 이 값으로 정렬하면 한국어 문헌이 항상 최하위로 밀립니다. 영어 논문은 정상적으로 옵니다(Search Agent 경유 실측에서 221, 312 등). **인용 수 결측은 언어·데이터 커버리지 문제이지 필드 자체의 문제가 아닙니다.**

**특허가 논문 결과에 섞입니다.** 학술 문헌만 기대하고 화면에 "논문"이라 표기하면 특허가 논문으로 표시됩니다.

**저자 목록에 같은 이름이 중복으로 들어올 수 있습니다.** `authors` 배열을 그대로 나열하기 전에 중복 제거가 필요합니다.

#### 코퍼스에 대한 관찰 — 여기부터는 추정입니다

관측 사실은 세 가지입니다. ① Scholar 단독 결과에 `openalex.org` URL이 직접 등장했고, ② `journal` 필드 표기가 OpenAlex의 source 표기와 닮았으며, ③ Search Agent 경유의 논문 검색은 `search_engine: "semanticScholar"`를 명시합니다.

여기서 "학술 백엔드가 둘"이라고 읽고 싶어지지만, **확정할 수 없습니다.** Liner는 회사 미팅에서 자체 논문 DB를 보유한다고 밝힌 바 있어, 다른 설명도 똑같이 성립합니다 — 자체 코퍼스 하나에 OpenAlex·Semantic Scholar 등 복수 공개 색인을 적재해 두고, 경로마다 다른 소스 라벨이 노출되는 그림입니다. `corpus_id`가 공개 식별자가 아니라 Liner 내부 UUID였다는 관측(§4-3)은 오히려 이 자체 DB 설명과 잘 맞습니다. 외부 호출만으로는 두 그림을 가릴 수 없습니다.

확실한 것은 결과로 드러난 성질뿐입니다 — **같은 논문 검색인데 경로에 따라 `citationCount`에 담겨 오는 값이 딴판입니다.** 단독 Scholar는 값이 낮거나 0이고(한국어 논문은 전부 0), 에이전트 경유는 실제 피인용 횟수에 가까운 값이 옵니다. 원인이 백엔드 분리든 적재 소스 차이든, 소비자 입장의 대처(한국어 `citationCount` 0을 결측으로 취급)는 같습니다.

## 4. Agent API

### 4-0. 사다리에서의 위치

Liner API는 **일을 몇 단계까지 대신 해 주느냐**로 나뉩니다.

| API | 하는 일 |
|---|---|
| Search API | 검색한다. 끝 |
| Quick Answer | 검색 1번 → 읽는다 → 답을 쓴다 |
| Search Agent | **검색어를 다시 써서** 여러 개 던진다 → 답을 쓴다 |
| Deep Research | 검색어를 나눠 던진다 → **결과를 읽고 더 깊은 검색어를 만든다** → 리포트를 쓴다 |

**"에이전트"는 여러 단계를 알아서 밟는 프로그램**입니다. Search API는 시킨 것 하나만 하고 끝나니까 에이전트가 아니라 "도구(Tools)"로 분류됩니다.

---

### 4-1. 에이전트 공통 — 입력 이해하기

#### `messages`가 왜 배열인가

**대화를 이어갈 수 있게 하려고**입니다.

한 번만 물을 때:

```json
{ "messages": [ {"role": "user", "content": "프랑스의 수도는?"} ] }
```

이어서 물을 때는 **앞 대화를 통째로 다시 보냅니다**:

```json
{ "messages": [
    {"role": "user",      "content": "프랑스의 수도는?"},
    {"role": "assistant", "content": "파리입니다."},
    {"role": "user",      "content": "거기 인구는?"}
]}
```

"거기"가 파리인 걸 알려면 앞 대화가 필요합니다.

**Liner 서버는 앞 대화를 기억하지 않습니다.** 매번 우리가 전부 다시 보냅니다. 대화가 길어질수록 요청이 커집니다.

| `role` 값 | 뜻 |
|---|---|
| `"user"` | 사람이 한 말 |
| `"assistant"` | **AI가 이전에 한 말.** 서버가 기억을 못 하니 우리가 알려주는 것 |

"마지막 항목의 role은 반드시 `user`"인 이유는 **답할 질문이 마지막에 있어야** 하기 때문입니다.

**이 무기억이 우리에게는 기회입니다.**

서버가 기억을 안 하니, "앞 대화"에 무엇을 넣을지는 우리가 정합니다. 실제로 있었던 대화일 필요가 없습니다. 예를 들어 이렇게 보낼 수 있습니다.

```json
{ "messages": [
    {"role": "user",      "content": "내 노트 맥락: 운영체제 과목. '데드락'은 '은행원 알고리즘', '자원 할당 그래프'와 연결돼 있음"},
    {"role": "assistant", "content": "맥락을 확인했습니다."},
    {"role": "user",      "content": "데드락 회피 기법의 정의가 맞는지 확인해줘"}
]}
```

첫 두 턴은 대화가 아니라 **우리 그래프에서 뽑아 꾸며 넣은 맥락**입니다. Liner는 이걸 이전 대화로 믿고 움직입니다. 멀티턴 실측(§4-2)에서 앞 대화가 내부 검색어까지 바꾸는 것을 확인했으니, 이 방법으로 검색 방향을 우리 쪽으로 끌 수 있습니다.

덤이 두 가지 있습니다.

- 같은 `messages`를 보내면 같은 조건으로 다시 실험할 수 있습니다 — 평가 스크립트에 유리합니다
- 필기의 어느 부분이 밖으로 나가는지 요청마다 우리가 정합니다 — 로컬 우선 원칙과 맞습니다

여기서 과금 방식을 함께 봐야 합니다. Liner는 **토큰이 아니라 성공한 호출 1회 단위로 정액 과금**합니다(§2 과금). **맥락을 얼마나 싣든 요금은 같습니다.** 늘어나는 것은 요청 본문의 크기와 그에 따른 전송 시간이며, 요청 크기 상한은 문서에 없습니다(§10).

#### `request_id`

**우리가 붙이는 이름표**입니다. 응답의 `start` 이벤트에 그대로 돌아옵니다.

```
보낼 때:  request_id = "concept-교착상태"
받을 때:  {"type":"start", "message_metadata":{"request_id":"concept-교착상태"}}
          → 이건 교착 상태 검증 결과구나
```

요청 30개를 동시에 던졌을 때 **어느 응답이 어느 요청인지 짝지으려고** 씁니다. 안 넣어도 동작합니다.

#### `stream` — 화면에 타이핑을 보여줄 것인가

```
[스트리밍 아님 · stream: false]
요청 → … 3초 동안 빈 화면 … → "파리는 프랑스의 수도입니다." 한꺼번에

[스트리밍 · 기본값]
요청 → 0.3초 "파리는"
       0.5초 " 프랑스의"
       0.7초 " 수도입니다."
```

**총 걸리는 시간은 같습니다.** 사용자가 기다리는 체감만 다릅니다.

`stream: false`를 쓰면 SSE 파싱 코드가 통째로 필요 없어집니다.

#### 라우터 — `data-search-decision`이 경로를 알려줍니다

에이전트가 질의를 어떤 경로로 처리할지 정한 결과가 이 이벤트로 노출됩니다.

| API | `decision` 값 | 비고 |
|---|---|---|
| Quick Answer | **이벤트 자체가 없음** | 라우터를 타지 않음 (2회 확인) |
| Search Agent | `"decompose"` | 검색어 분해. 4회 전부 동일 |
| Deep Research | `"deepResearch"` | 1회 관측 |
| Visual Answer | `"image-generation"` 또는 미발생 | 그림을 요청하면 이미지 경로로 빠짐 |

같은 이벤트에 부속 필드가 함께 옵니다. 전부 문서에 없는 것들입니다.

```json
{"decision": "decompose", "isEssayModeWritingStyleOn": false}
{"isScholarlyQuery": false}
{"isReferenceIntentAnswer": false}
```

`isEssayModeWritingStyleOn`은 미공개 문체 기능의 존재를, `isScholarlyQuery`는 general 모드에서도 학술 질의 여부를 판정한다는 것을 드러냅니다. 켜는 방법은 문서 어디에도 없습니다.

2026-08-25 실측(간격 반복 4회)에서 라우터 앞뒤로 **처음 보는 이벤트들**이 관측됐습니다. 분류기가 하나가 아니라 여러 개입니다.

```
query_classification              → categories: ["Casual"], intents: ["Analysis"]
sensitive_query_classification    → categories: ["Others"]        (민감 질의 분류기가 따로 돎)
researchagent_query_classification → agent: null
data-metadata                     → answerMode: "search", languageCode: "ko"
```

같은 실행의 메타데이터에 **문서에 없는 요청 옵션처럼 생긴 필드 3개**도 노출됐습니다: `blockedDomains: []`, `forcedSingleSearch: false`, `scholarReferenceFilter: null`. 도메인 차단·단일 검색 강제·논문 필터가 내부적으로 존재한다는 뜻인데, REST 요청에 넣으면 받아 주는지는 미확인입니다(§10).

한 가지 주의: `isScholarlyQuery`는 정의형 질문·general 모드에서도 `true`로 왔습니다(4회 전부). **이 플래그로 논문 검색 여부를 예측할 수 없습니다** — 실제 갈림은 §4-3의 도구 선택 단계에서 일어납니다.

#### 본문 인용은 어디서 붙는가 — 최종 매트릭스

인용 지시를 넣고 빼며 네 조합을 실측한 결과입니다.

| 실행 | 경로 | 인용 지시 | 본문 인용 수 |
|---|---|---|---|
| PKM 조사 | Search Agent `general` | 없음 | 1 |
| entity resolution | Search Agent `scholar` | 있음 | **94** |
| 증분 갱신 조사 | Deep Research | 있음 | **40+** |
| 링크 UX 조사 | Search Agent `general` | **있음** | **2** |

> **결론: 본문 인용은 `mode: scholar`와 Deep Research에서만 붙습니다.** general·Quick Answer·Visual Answer는 지시해도 안 붙습니다. 인용 지시는 되는 경로 안에서 밀도를 높일 뿐입니다.

#### 프롬프트 지시문의 실제 효과

여러 실행에 지시를 걸어 본 채점표입니다.

| 지시 | 효과 | 근거 |
|---|---|---|
| "답변은 한국어로 작성하라" | ✅ 작동 | 안 걸면 출처 언어를 따라 영어로 이탈한 사례 있음 (Quick Answer) |
| "근거 없으면 '확인된 자료 없음'이라 적어라" | ✅ 작동 | Search Agent·Deep Research에서 반복 확인. 지시한 표현 그대로 씀 |
| 출력 형식 지정 (판정 라벨, 문장 단위 인용 번호) | ❌ 무시되기 쉬움 | Quick Answer는 [참/거짓] 라벨 무시, general은 인용 번호 무시 |
| 검색 범위 제한 (SEO·마케팅 제외 등) | ❌ **검색어에 전달 안 됨** | 검색어에 제외 연산자 0회. 출처 목록 오염. 본문 방어는 간헐 작동 |
| "출처에 없는 수치를 쓰지 마라" | △ 절반 | 수치 창작은 막지만, **무관한 실측치를 관련 있는 것처럼 배치**하는 것은 못 막음 |

#### 대화 맥락은 검색까지 전달됩니다

`messages`에 앞 대화를 붙이고 "두 번째 주장에서 다룬 그 논문"처럼 앞 턴 없이는 해석 불가능한 질문을 던지자, 검색 결과 자체가 정확히 그 논문의 서지 페이지들로 왔습니다. **대화 이력이 답변 생성뿐 아니라 검색어 재작성에도 쓰입니다** (Quick Answer 실측).

#### `trace_id`가 API를 식별합니다

`start` 이벤트의 `message_metadata.trace_id` 접두사가 내부 API 이름입니다.

```
api_quick_answer_c4320e61   api_visualization_d60f1c75
```

로그를 API별로 가를 때 이 접두사를 쓸 수 있습니다.

### 4-2. Quick Answer Agent API

> **한 줄로**
> 검색까지 대신 해 주고 답까지 써 주는 API. Search API가 링크 목록만 준다면, 이건 그 링크들을 읽고 정리한 답을 준다.

**엔드포인트**: `POST /api/v1/agents/quick-answer`

**입력**

| 필드 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `messages` | array | 필수 | 대화 이력. 마지막 항목의 `role`은 반드시 `"user"` |
| `messages[].role` | string | 필수 | `"user"` 또는 `"assistant"` |
| `messages[].content` | string | 필수 | 메시지 본문 |
| `request_id` | string | 선택 | 클라이언트 식별자 |
| `stream` | boolean | 선택 | 기본 `true` |

**`mode`도 `model`도 없습니다.** 항상 웹 검색만 하고, Liner가 정한 모델로 고정입니다. 같은 질문을 나중에 다시 던졌을 때 같은 답이 나온다는 보장이 없습니다.

**단가**: 1,000회당 $3 / **QPS 제한 없음**

#### 실측 결과 ① — "머신러닝이 뭔가요?"

- 이벤트 **13개**
- 출처 **3개**: IBM 한국어판(`ibm.com/kr-ko/`), SK하이닉스 뉴스룸, SAP
- 답변 2문장, 정확

**한국어 질문에 한국어판 IBM 페이지를 정확히 찾아왔습니다.** 영어 페이지를 던져주지 않았습니다.

#### 실측 결과 ② — 틀린 주장 검증

일부러 틀린 내용을 필기라고 제시하고 물었습니다.

```
질문: "제 필기에 '다익스트라 알고리듬은 음수 가중치 간선이 있는 그래프에서도
       최단 경로를 보장한다'고 적혀 있습니다. 이 내용이 맞나요?"

답변: "다익스트라 알고리즘은 음수 가중치가 있으면 최단 경로를 보장하지 않습니다.
       이미 확정된 노드보다 더 짧은 경로가 뒤늦게 발견될 수 있어
       그리디 방식의 한계가 발생하기 때문입니다."
```

**첫 문장부터 반박했고 이유도 정확합니다.** 사용자 편을 들지 않습니다.

- 이벤트 **13개**
- 출처 **2개**: 티스토리 개인 블로그, coddy.tech

#### 출처 수는 고정이 아닙니다

```
"머신러닝이 뭔가요?"        →  3개
"다익스트라 음수 가중치…"    →  2개
```

`max_results` 같은 조절 파라미터가 없고, 개수는 질문에 따라 Liner가 정합니다.

| | 출처 수 |
|---|---|
| Web Search | 10개 (`max_results`로 최대 20까지) |
| Quick Answer | **2~3개.** Liner 내부 기준, 조절 불가 |

#### 출처 품질은 주제에 따라 갈립니다

| 질문 | 출처 |
|---|---|
| "머신러닝이 뭔가요?" | IBM 한국어판 · SAP · SK하이닉스 (기업 공식 문서) |
| "다익스트라 음수 가중치…" | **티스토리 개인 블로그** · 소규모 시각화 사이트 |

**대중적 주제에는 기업 공식 문서가 있지만, 교과 개념에는 한국어 권위 출처가 없어서 개인 블로그로 내려갑니다.** 다만 내용은 두 건 다 정확했습니다.

#### 문서와 실제가 다른 곳 (2회 모두 동일)

| 문서 | 실제 |
|---|---|
| 답변에 인용 번호 `[1]`이 붙는다 | **안 붙는다** |
| `data-search-chunks`가 답변↔출처를 연결해 준다 | **그 이벤트가 아예 안 온다** |
| 출처가 답변보다 먼저 온다 | **반대다.** 답변이 다 나온 뒤 출처가 온다 |

실제 이벤트 순서는 이랬습니다.

```
start → start-step
      → text-start → text-delta ×4          ← 답변이 먼저
      → data-search-references               ← 출처가 나중
      → data-update(finish_answer)           ← 문서에 없는 이벤트
      → text-end → finish-step → finish → [DONE]
```

**문서에 없는 `data-update` 이벤트에 완성된 답변 전문이 통째로 들어 있습니다.**

```json
{
  "type": "data-update",
  "data": { "event": "finish_answer", "data": { "answer": "머신러닝은 …" } }
}
```

조각을 이어 붙일 필요 없이 이것만 잡으면 됩니다.

#### 인용 매핑이 없어도 근거를 검사할 수 있습니다

답변과 출처의 어휘를 겹쳐 보면 됩니다.

```
답변:   "이미 확정된 노드보다   더 짧은 경로가  뒤늦게 발견될 수 있어"
출처2:  "나중에 이미 확정된 노드로 가는 더 짧은 경로를  만들어"
         ^^^^^^^^^^^^^^^^^^  ^^^^^^^^^^^^^
```

**어휘가 겹치면 근거가 있는 것이고, 하나도 안 겹치면 지어낸 것으로 의심합니다.** 문자열 비교라 비용이 0입니다.

#### 추가 실측 (3회 · 2026-08-25) — 판정자가 아니라 근거 조달자입니다

틀린 주장 3개(참 1, 연도 오류 1, 귀속 오류 1)를 주고 `[참/거짓/판단 불가]` 라벨을 요구했습니다.

| 요구 | 결과 |
|---|---|
| 연도 함정 (LSTM 1995) | ✅ 1997로 정정된 사실을 서술 |
| 귀속 함정 (드롭아웃=르쿤) | ✅ 힌튼으로 정정된 사실을 서술 |
| 참인 기준선 (트랜스포머 2017) | ❌ **검증 자체를 건너뜀** |
| `[참/거짓]` 라벨 | ❌ **전부 무시.** "거짓이다"라는 문장이 없음 |

**올바른 사실을 말할 뿐, 원 주장과 대조해 판정하지 않습니다.** 판정은 답변을 받아서 우리 쪽에서 내려야 합니다. 그리고 주장 여러 개를 한 호출에 묶으면 일부를 건너뜁니다 — 검증 용도라면 주장당 1호출이 맞습니다.

**멀티턴이 실제로 동작합니다.** `assistant` 턴을 붙이고 "두 번째 주장의 그 논문 원제는?"을 물었더니 정확히 해석해 서지를 찾아왔습니다.

**답변 언어가 질문이 아니라 출처를 따라갈 수 있습니다.** 한국어로 물었는데 검색 결과가 영어 학술 페이지(ResearchGate·PubMed)뿐이자 **답변이 영어로 왔습니다.** 언어를 고정하려면 지시문에 명시해야 합니다.

**출처 품질은 질문 유형이 정합니다.** 개념 질문에는 블로그, 서지 질문에는 학술 DB가 왔고, 그 안에 **sci-hub**가 출처로 등장했습니다. 출처 필터는 적법성 검사를 하지 않습니다.

**`data-search-decision` 이벤트가 없습니다.** Quick Answer는 라우터를 타지 않습니다. 속도(2.6~3.4초)가 일곱 API 중 가장 빠른 이유이기도 합니다.

#### `date` 형식이 또 다릅니다

```
Web Search    : null           또는  "2026-05-29"
Scholar Search: ""             또는  "2016"  또는  "2016-09-01"
Quick Answer  : ""             또는  "Jun 25, 2024"     ← 영문 축약 월
```

**같은 회사 API 셋이 날짜 표현을 전부 다르게 합니다.**

### 4-3. Search Agent API

> **한 줄로**
> Quick Answer의 윗급. 질문을 검색어로 다시 써서 여러 번 찾고, 인용 붙은 긴 답을 써 준다. 대신 7배 비싸고 느리다.

**엔드포인트**: `POST /api/v1/agents/search`

**입력**: Quick Answer의 파라미터에 셋이 추가됩니다.

| 필드 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `mode` | string | 선택 | `general`(기본) 또는 `scholar` |
| `model` | string | 선택 | 모델 식별자. **선택 가능한 값 목록이 문서에 없고 플레이그라운드에도 UI가 없음** |
| `lang` | string | 선택 | 언어. **설명 문장이 문서에 없음** |

**`mode`는 자율이 아니라 우리가 고릅니다.** 레퍼런스 원문이 "검색 모드: `general`(기본) 또는 `scholar`"입니다. "또는"이므로 택일입니다.

**`model`은 현실적으로 없는 파라미터로 취급하는 게 맞습니다.** Liner 자신도 플레이그라운드에 노출하지 않습니다.

**단가**: 1,000회당 $20 / 2 QPS

#### 핵심 차이 — 질문을 그대로 검색하지 않습니다

```
우리가 던진 것:  "제 필기에 '다익스트라는 음수 가중치에서도 최단 경로를
                  보장한다'고 적혀 있습니다. 맞나요?"
       ↓  Liner가 알아서 만든 검색어
       1. "다익스트라 알고리즘 음수 가중치 간선 사용 가능 여부"   ← 한국어 검색어로 압축
       2. "Dijkstra's algorithm negative edge weights constraints"  ← 영어로 번역
       3. (원문 그대로)
```

**한국어와 영어 양쪽으로 검색했습니다.** 그래서 stackoverflow, GeeksforGeeks, usaco.guide 같은 영어권 출처가 딸려 왔습니다. Quick Answer가 티스토리 2개만 준 것과 대비됩니다.

#### 실측 결과 — 질문에 따라 완전히 다르게 행동합니다

세 번 던진 결과입니다.

| | 다익스트라 (general) | 다익스트라 (scholar) | GraphRAG (scholar) |
|---|---|---|---|
| 호출된 도구 | `search_web` | **`search_web`** | `search_papers` |
| 출처 | 23개 | 23개 (순서까지 동일) | **45개** |
| 이벤트 | 302개 | **1,430개 이상** | — |
| 시간 | 18.5초 | **53.3초** | — |
| 답변 섹션 | 3개 | **26개** | 7개 |
| 답변 분량 | 약 900자 | 약 4,500자 | 약 2,000자 |
| 인용된 출처 | 1개 (4%) | 1개 (4%) | **20개 이상 (45%)** |
| 길이 상한 도달 | 아니오 | **예** | 아니오 |

#### `mode`의 정체 — 통제 실험 4회 (2026-08-25, 주제: 간격 반복)

"scholar는 무조건 논문이 아니라 필요하면 논문도"라는 초기 관측을 검증하려고, 같은 주제로 질문의 학술성 프레이밍만 바꾼 4회를 돌렸습니다.

| 실행 | 질의 프레이밍 | mode | `search_papers` | `search_paper_sections` | `search_web` | 출처 | 본문 인용 |
|---|---|---|---|---|---|---|---|
| Q1 | 정의형 ("무엇인지 설명해줘") | scholar | 실행 | — | 실행 | 논문 4 + 웹 36 | 3회, 논문 1편 |
| Q3 | 근거형 ("근거는 뭐야?") | scholar | 실행 | 실행 | 실행 | 105 (최다) | 중간 밀도 |
| Q2 | 연구형 ("실험 연구 결과들을 알려줘") | scholar | 실행 | 실행 | — | 논문만 72 | 조밀, 20편 이상 |
| Q7 | Q2와 동일 질의 | **general** | **미실행** | **미실행** | 실행 (5개 검색어) | 웹 53 | **0** |

세 가지가 확정됩니다.

1. **`mode`는 도구 접근 권한입니다.** general은 연구 결과를 명시적으로 요구받아도 논문 인덱스에 못 갑니다 — 웹 검색만 돕니다. 비대칭이 핵심입니다: scholar는 웹으로 내려갈 수 있지만, general은 논문으로 올라갈 수 없습니다. 단가는 모드 무관 동일이므로, 학술 근거가 필요한 용도라면 general을 고를 이유가 없습니다.
2. **scholar 안에서는 질문의 학술성이 눈금입니다.** 논문 초록 검색(`search_papers`)은 항상 돌고, "근거"라는 단어만 있어도 논문 **절 단위 검색**(`search_paper_sections` — 이 실험에서 처음 관측된 세 번째 검색 도구, Discussion 절·그림 캡션까지 가져오며 원출력의 `section_idx`를 채움)이 추가되며, "연구 결과들을 알려줘"처럼 문헌 자체를 요구해야 웹 채널이 꺼집니다. 인용 밀도도 같은 눈금을 따라 3회 → 중간 → 20편 이상으로 늘었습니다.
3. **라우터 플래그는 이 갈림을 예고하지 않습니다.** `isScholarlyQuery`는 4회 전부(general 포함) `true`였습니다. 실제 갈림은 그 뒤 도구 선택 단계에서 일어납니다.

general 모드의 품질도 따로 기록할 가치가 있습니다. 웹 검색으로도 pubmed·sciencedirect 같은 학술 **페이지**는 잡히지만, ① `citationCount`·저자·저널이 전부 null이 되고(인용 수는 "779회 인용" 같은 구글 스니펫 문자열로만 존재), ② 핵심 수치가 2차 출처를 경유하며(Cepeda 2006의 수치를 Facebook 페이지에서 인용), ③ "학습 효과 메타분석"이라는 표면 유사성만 있는 무관 문서(생성형 AI·플립러닝·하브루타·PBL)가 대거 혼입됐습니다. scholar(Q2)에서는 셋 다 없던 문제입니다.

같은 실험에서 재확인·신규 관측된 것: 같은 논문이 URL만 다르게 두 번 들어오는 사례 2건 추가(APA 정식 URL 인용 263 vs 대학 PDF 인용 0 · Cell Reports 출판본 vs bioRxiv 프리프린트 — 출판본/프리프린트 판별도 안 됨), 내부 검색어 연도 접미사("… 2026") 재확인, 웹 채널 엔진 라벨 `search_engine: "google"` 명시, Q3에서 `finish_subtask` 2회 호출(하위 과제 2개였는지는 `tasks` 이벤트 미수집으로 미확정 — §10).

#### 답변 길이 상한이 있습니다

scholar 모드의 다익스트라 실행이 상한에 닿았습니다.

> "답변이 길어져 여기서 마칩니다. 이어서 보고 싶으시면 계속 써달라고 말씀해 주세요."

**에러가 아니라 자연어 안내로 끊고 `finish` 이벤트는 정상적으로 나옵니다.** 응답 구조만 봐서는 완결된 답변과 구분되지 않습니다. 이어서 받으려면 `messages`에 이 답변을 `assistant`로 붙이고 재호출해야 하며, 한 번 더 과금됩니다.

상한값 자체는 재지 못했습니다. 관측은 "닿으면 이렇게 끊긴다"는 동작 1회뿐이고, 몇 자(또는 몇 토큰)에서 끊기는지, 그 값이 고정인지는 모릅니다. 끊는 주체가 모델이라 잘리는 지점도 문장 단위로 흔들릴 것이므로, 값을 재려면 잘림을 여러 번 유도해 잘린 길이가 한 값 근처에 모이는지 봐야 합니다. 비용 대비 소득이 낮습니다 — 우리 대처(잘림 안내 문구 감지)는 상한값을 몰라도 같기 때문입니다.

#### 26섹션이 좋은 게 아니었습니다

같은 출처 23개로 답변만 5배 길어진 실행인데, 늘어난 섹션 대부분이 알맹이가 없었습니다.

> "여러 자료가 지적하듯이…"  "여러 기술 문서가 명확히 적시하고 있으며…"

어느 자료인지 지목도 안 하고 인용 표시도 없습니다.

그리고 시간복잡도 수치(`O((V+E)log V)`, `O(V·E)`)를 제시하는데, **23개 출처 어디에도 그 내용이 없고 인용 표시도 없습니다.** 모델이 자기 지식에서 꺼내 섞은 것입니다.

**이게 문제인지는 용도에 따라 갈립니다.** 답만 원하는 사용자에게는 문제가 아닙니다 — 위 수치는 교과서 지식으로 맞고, 모델의 지식이 답을 좋게 만들었다면 그만입니다. 문제는 **근거를 사는 소비자**의 입장입니다. 우리가 Quick Answer의 7배 값을 내고 Search Agent를 부르는 이유는 답변이 아니라 **검색이 확인해 준 근거**인데, 모델 기억에서 나온 문장이 근거 있는 문장과 같은 얼굴로 나오면 어느 쪽이 어느 쪽인지 가릴 표시가 없습니다. 모델 기억이 맞을 때(다익스트라)는 무해하지만, 틀릴 때 알아챌 방법이 없다는 게 핵심입니다 — 앞서 본 인용 미끄러짐 3단계가 바로 그 "틀리는데 표시는 멀쩡한" 경우입니다. 모델 지식만으로 충분한 질문이라면 애초에 훨씬 싼 경로(우리 파이프라인의 Gemini 호출)로 됩니다.

반면 GraphRAG 질문의 7섹션 답변은 출처에서 실제 수치를 뽑아 씁니다.

```
"vanilla RAG 대비 최대 24.4% 절대 향상(Exact Match 기준)"
"5-홉 F1에서 0.772 vs 0.170"
"10–20× 높은 리소스 소비"
```

**출처가 두 배 많은 쪽이 답변은 절반이었습니다.**

#### 반복 검색의 실체

```json
{"type":"data-search-decision", "data":{"decision":"decompose"}}
{"type":"data-metadata",        "data":{"forcedSingleSearch": false}}
{"type":"data-search-tasks",    "data":{"tasks":[ 1개 ]}}
```

**"분해하기로 결정"하고 "단일 검색을 강제하지 않았다"고 하면서 과제를 1개만 만들었습니다.** 실행 전부에서 그랬습니다.

가격 페이지는 "반복 검색"이라 하고 레퍼런스는 "단일 패스"라고 해서 모순처럼 보였는데, **양쪽이 반씩 맞았습니다.** 반복 능력은 있으되 질문이 복잡할 때만 발동합니다.

#### 추가 실측 (4회 · 2026-08-24~25) — 복잡한 질문에서는 진짜로 반복합니다

여러 항목을 담은 조사형 질문 4회는 **전부 2~3라운드**를 돌았습니다. 라운드 수는 고정이 아니고, 총 검색어는 15개 안팎이었습니다.

| 실행 | 라운드 | 검색어 |
|---|---|---|
| PKM 4항목 (general) | 3 | 5+6+4 = 15 |
| entity resolution (scholar) | 3 | 15 |
| 링크 UX 조사 (general) | **2** | 7+8 = 15 |
| granularity 논문 (scholar) | 2 | 15 |

라운드가 진행되며 검색어가 **진화합니다.**

- 문법이 발전함: 자연어 → 따옴표 구문 → 도메인 한정어 추가
- 1라운드에서 알아낸 고유명사를 2라운드 검색어에 박음
- **이미 찾은 항목은 다음 라운드에서 빠지고, 못 찾은 항목만 남음**

#### 인용 번호의 실체 — passage id

`data-search-chunks` 이벤트의 `referenceChunks[].num`(1~136)이 본문 인용 번호의 원본입니다. scholar 실행에서는 엔진이 답변 안에 규약을 직접 써 놓기까지 했습니다.

> "예: 5는 문헌 id=4의 **passage id=5**를 의미한다"

즉 인용 번호는 문서 단위가 아니라 **절(passage) 단위**입니다. 같은 논문이 절 4·18·23으로 세 번 결과에 등장하는 이유입니다.

#### 도구 원출력과 최종 참조의 명명 규칙이 다릅니다

| 층 | 예 |
|---|---|
| 도구 원출력 (`data-update`의 `output`) | `citation_count`, `section_idx`, `relevance_score` (snake_case) |
| 최종 참조 (`data-search-tasks`의 `output.references`) | `citationCount`, `sectionIdx`, `relevanceScore` (camelCase) |

같은 데이터가 파이프라인 층에 따라 이름이 다릅니다. 파서는 두 형태를 다 받아야 합니다. 또 `corpus_id`는 Semantic Scholar의 정수 ID가 아니라 **Liner 내부 문서 UUID**입니다.

#### 점수 4종은 하이브리드 채널의 흔적입니다

결과마다 `lexicalScore` / `sparseScore` / `vectorScore` 중 일부만 채워집니다 — 채널별 검색이 따로 돌고 걸린 채널의 점수만 남습니다. 세 채널 모두에서 잡힌 문서가 `retrievalScore` 최고값(0.0254)을 받았고, 값의 꼴이 순위 역수 합(1/80≈0.0125 등)이라 **순위 역수 융합(RRF)으로 추정**됩니다. 정렬키는 `relevanceScore`(0.22~0.31 내림차순)입니다.

#### 언제 멈추는가

```json
{
  "tool": "finish_subtask",
  "reason": "I have gathered sufficient research papers (2024-2026) that provide
             specific quantitative and qualitative comparisons between GraphRAG and
             traditional Vector RAG… providing a solid foundation for a comprehensive answer."
}
```

**고정 횟수가 아니라 에이전트가 "충분하다"고 판단하면 멈춥니다.** 그 판단 근거를 자연어로 남깁니다.

#### 문서에 없는데 유용한 이벤트 세 개

**① `answerBox` — 한 줄 판정을 따로 줍니다**

```json
{
  "type": "data-rich-content",
  "data": { "answerBox": { "data": "**아니요, 틀렸습니다**" } }
}
```

긴 답변을 파싱해서 "맞다/틀리다"를 뽑을 필요가 없습니다.

**② `data-highlight-phrases` — 핵심 문장을 뽑아 줍니다**

```json
{
  "highlightPhrases": [
    "당신의 필기 \"다익스트라 알고리듬은 …보장한다\"는 문장은 틀렸습니다 ((2))."
  ]
}
```

**③ `query_classification` — 질문 의도를 분류합니다**

```json
{"categories": ["Casual"]}
{"intents": ["Fact-check"]}
```

Liner가 이 질문을 `Fact-check`로 분류했습니다.

#### 검색 엔진이 응답에 적혀 있습니다

```json
"searchEngine": "google",           ← 웹 검색
"searchEngine": "semanticScholar",  ← 논문 검색
```

Search API 응답에는 없던 필드이고 Search Agent의 도구 출력에만 노출됩니다.

#### 논문 검색일 때만 오는 것

`search_papers`가 돌면 참조 객체에 필드가 30개 넘게 붙습니다.

```
citationCount   327, 155, 86, 78, 41…     ← Scholar API 단독(최대 15)보다 훨씬 정확
doi             "10.48550/arxiv.2408.08921"
authorsWithId   저자별 고유 ID
publicationType preprint / article / dissertation / conference-paper / software
pdfUrl, isOpenAccess, hasFullText, hasCitations, hasReferences
```

**같은 회사의 학술 검색인데, 경로에 따라 `citationCount`에 담겨 오는 값이 딴판입니다.** 값 자체의 문제이지 "인용의 품질" 이야기가 아닙니다 — Scholar API 단독은 값이 낮거나 0으로 오는 경우가 많았는데, Search Agent 경유는 실제 피인용 횟수에 가까운 값이 옵니다. 왜 다른지는 확정하지 못했습니다 — 백엔드가 둘일 수도 있고, 자체 코퍼스에 적재한 소스가 경로마다 다를 수도 있습니다(§3-2 "코퍼스에 대한 관찰"의 추정 논의). 대처는 원인과 무관합니다: 이 필드를 쓸 거면 Search Agent 경유 값을 기준으로 삼고, Scholar 단독의 0은 결측으로 취급해야 합니다.

**SJR 학술지 등급이 통째로 옵니다.**

```json
"publicationVenueStruct": {
  "issn": "1942-4787",
  "name": "WIREs Data Mining and Knowledge Discovery",
  "type": "journal",
  "sjrBestQuartile": "Q1",
  "sjrRank": 1197,
  "sjrScore": 2202,
  "sjrHIndex": 79,
  "sjrCountry": "United States"
}
```

`authorityScore` 필드는 **끝까지 `null`**이었습니다. 실질적인 권위 지표는 이 자리에 있습니다.

**다만 메타데이터가 섞여 있습니다.**

```json
{
  "name": "arXiv (Cornell University)",   ← 저장소 이름인데
  "issn": "1046-8188",                     ← ACM TOIS의 ISSN
  "sjrBestQuartile": "Q1",
  "doi": "10.1145/3777378"                 ← ACM 학술지 DOI
}
```

arXiv 프리프린트가 정식 학술지에 게재되면서 이름만 arXiv로 남았습니다. **`journal` 필드를 그대로 표시하면 "arXiv에 실렸다"고 잘못 표기됩니다.**

#### 하이브리드 검색 구조가 드러납니다

점수가 넷인데 문서마다 채워진 것이 다릅니다.

| 문서 | `lexicalScore` | `sparseScore` | `vectorScore` |
|---|---|---|---|
| Polymer Knowledge | `null` | 17623134 | `null` |
| From Embeddings to Entities | 58.78 | 16501701 | 0.338 |
| Practical Study of Trade-offs | 58.38 | `null` | `null` |
| WIREs Advanced Review | `null` | `null` | 0.357 |

**어휘 검색·희소 검색·벡터 검색을 병렬로 돌리고 걸린 경로의 점수만 남깁니다.**

스케일도 제각각입니다. `sparseScore`는 1,500만~2,100만대 정수이고 나머지는 0~1 또는 40~80대입니다.

### 4-4. Deep Research Agent API

> **한 줄로**
> Liner에서 제일 비싼 API. 검색을 여러 바퀴 돌고 목차 있는 리포트를 써 준다. 출처를 백 개 넘게 물어 오는데, 그중에 엉뚱한 게 섞인다.

**엔드포인트**: `POST /api/v1/agents/deep-research`

**입력**: `messages`(필수), `request_id`, `stream`, `lang`

**`mode`도 `model`도 없습니다.** 웹을 볼지 논문을 볼지 에이전트가 알아서 정합니다.

**단가**: 1,000회당 $200 / 2 QPS. **한 번에 20센트.** Quick Answer($3)의 67배, Search Agent($20)의 10배입니다.

문서가 "복잡한 질의는 수 분이 걸릴 수 있으므로 백엔드에서 호출하기를 권장"한다고 명시합니다.

#### 6회 실측 요약

이 절은 6회 실측 기록을 회차별로 수록하므로 분량이 많습니다. 아래 표는 회차별 상세에서 확인된 사항을 항목별로 정리한 것입니다.

| 물어본 것 | 답 | 근거 |
|---|---|---|
| 질문을 여러 조사 과제로 쪼개 주는가 | **아니오.** 11회 연속 1개 | 실측 ① |
| 검색은 몇 바퀴 도는가 | **2~4회 가변.** 고정 아님 | 3~6차 |
| 논문도 찾아 주는가 | 최근 3회는 **웹만** 검색. 질문에 "학술 연구"라고 써도, 영어 학술 용어를 써도 논문 검색을 안 씀 | 4·5·6차 |
| 출처를 몇 개나 모으는가 | 80~180개. **많다고 좋은 게 아님** — 가장 많이 모은 실행이 품질은 최악 | 전 회차 |
| 답변에 인용을 조밀하게 다는가 | **들쭉날쭉.** 1%부터 100%까지. "출처 유형을 구분해 정리하라"고 요구하면 조밀해짐 | 4·5·6차 |
| 본문 내용은 믿을 만한가 | **주제에 달림.** 자료가 풍부한 주제는 수치까지 정확했고, 집계가 드문 주제는 비슷해 보이는 무관 수치로 채움 | 4차 vs 2·5차 |
| 지시를 걸면 나아지는가 | **부분적으로.** 금지형 지시("~하지 마라")는 잘 안 지켜지고, 형식 요구("수치와 대상을 같이 써라")는 출력 단계에서만 작동 | 3·6차 |

**확인된 실패 유형 다섯 가지**입니다. 자세한 사례는 각 회차 절에 있습니다.

| 유형 | 무슨 일이 일어나는가 |
|---|---|
| 동음이의어 오염 | 질문에 쓴 단어가 다른 분야에서도 쓰이면 무관한 문서가 딸려 옴 (`Obsidian` → 웹호스팅 패널·게임 스튜디오) |
| 검색어 발명 | 모델이 없는 약어를 만들어 검색함 (`MSR` → 화성 시료 회수 문서 유입) |
| 표 오귀속 | 다른 대상에서 측정된 수치를 관련 있는 자리에 놓음 |
| 출처 품질 붕괴 | 사람이 쓰지 않은 자동 생성 페이지를 1차 근거로 인용 |
| 검색어 조이기 | 원하는 수치를 못 찾으면 따옴표·와일드카드로 검색 문법을 조이다가, 결국 그 수치를 주장하는 저품질 페이지를 집음 |

리포트의 구조와 형식은 안정적으로 생성되나, 본문에 포함된 수치와 출처는 별도 검증이 필요합니다.

#### 문서상 이벤트 순서 읽는 법

```
start
 → start-step
 → data-search-tasks
 → (data-search-step → data-search-references → data-search-chunks)*
 → reasoning-start → reasoning-delta* → reasoning-end
 → text-start → text-delta* → text-end
 → [data-metadata]
 → finish-step → finish → [DONE]
```

기호 두 개만 알면 됩니다.

| 기호 | 뜻 |
|---|---|
| `( … )*` | 괄호 안이 **0번 이상 반복**됨 |
| `[ … ]` | **선택적.** 안 올 수도 있음 |

`reasoning-*`와 `text-*`가 **별개 스트림**입니다. id가 다르므로 "생각 중" 영역과 "본문" 영역을 따로 그릴 수 있습니다.

#### 실측 ① — 하위 과제는 1개였습니다

```
Research steps (1)
  GraphRAG를 실제 제품에 도입할 때 고려해야 할 사항을 조사해 주세요.
  성능, 비용, 구축 난이도, 평가 방법을 각각 다뤄 주세요.
  Completed
```

**네 항목을 명시했는데도 과제는 하나입니다.**

두 번째 실험에서는 아예 서로 다른 세 분야를 나열했습니다.

```
1. 문서에서 지식 그래프를 자동 구축하는 기법        (컴퓨터과학)
2. 세컨드 브레인 앱의 노트 연결 실사용 조사          (제품 사용성)
3. 개념 연결 학습의 기억 효과 인지심리학 연구        (심리학)
```

**그래도 과제는 1개였습니다.** Search Agent까지 합치면 이 시점에 **8회 연속 1개**였고, 이후 실측을 더해 지금은 **11회 연속**입니다. 【1】【2】로 명시적으로 번호를 매겨 나눠도 마찬가지였고, `task` 필드에는 질문 전문이 요약 없이 그대로 들어갑니다.

#### 검색어 재작성과 과제 분해는 뭐가 다른가

이게 가장 헷갈리는 지점입니다.

**Search Agent가 실제로 한 것**

```
하위 과제 1개
  └─ 검색어 3개
       "GraphRAG vs traditional RAG retrieval performance comparison study"
       "performance evaluation GraphRAG vs vector RAG metrics"
       "GraphRAG benefits over vector RAG research results"
```

**셋 다 같은 질문입니다.** 표현만 바꾼 것이고 묻는 내용은 하나입니다.

**과제 분해였다면 이런 모양이 됩니다**

```
하위 과제 1: GraphRAG와 기존 RAG의 구조적 차이는 무엇인가
하위 과제 2: 비교에 쓰인 벤치마크와 평가 지표에는 무엇이 있는가
하위 과제 3: 다중홉 질의에서의 수치 비교 결과는 어떤가
하위 과제 4: 비용과 지연 시간 측면의 측정치는 어떤가
```

**서로 다른 질문 넷입니다.** 각 과제가 자기만의 검색 사이클을 따로 돕니다.

**한 줄로 정리하면**

```
검색어 재작성 : 같은 질문을 여러 방식으로 검색한다   →  출처가 넓어진다
과제 분해     : 다른 질문 여러 개로 나눈다           →  답변의 목차가 생긴다
```

#### 실측 ② — 실제로는 "쿼리 분해"를 합니다

세 주제 질문의 1차 검색 쿼리입니다.

```
① latest techniques for automatic knowledge graph construction from documents 2026 LLM GraphRAG  ← 주제 1
② user survey Obsidian Notion note linking backlinks usage 2025 2026                             ← 주제 2
③ cognitive psychology research effect of connecting concepts on memory retention …              ← 주제 3
④ 문서 기반 지식 그래프 자동 구축 최신 기술 2026                                                  ← 주제 1 (한국어)
⑤ 옵시디언 노션 노트 연결 기능 사용자 통계 조사                                                   ← 주제 2 (한국어)
```

**세 주제를 정확히 나눠 담았습니다.** 영어 3개로 세 주제를 각각 덮고, 한국어 2개로 ①②를 보강했습니다.

```
❌ 질문을 여러 과제로 쪼개서 각각 조사한다
✅ 질문 하나를 유지한 채, 검색어를 주제별로 나눠 던진다
```

**과제 목록은 원문 질문을 담는 그릇 하나로만 쓰입니다.**

#### 실측 ③ — 검색은 진짜로 두 바퀴 돕니다

이건 Search Agent와 명확히 갈리는 지점입니다.

```
Tool calls (5)
  ① update_search_status     ← 검색 전 상태 갱신
  ② search_web   쿼리 5개    elapsedTime 3.41초  →  출처 65개
  ③ update_search_status     ← 1차와 2차 사이 상태 갱신
  ④ search_web   쿼리 6개
  ⑤ finish_subtask
```

**2차 쿼리는 1차 결과를 읽고 만듭니다.** 첫 실험에서 증거가 명확합니다.

| 1차 결과에 나온 문구 | 파생된 2차 쿼리 |
|---|---|
| Memgraph: "One major limitation is **entity resolution**" | `GraphRAG entity resolution best practices 2026` |
| OpenReview: "introducing **GraphRAG-Bench**" | `GraphRAG-Bench evaluation metrics details` |

**"여기 더 파야 할 게 있다"고 판단해서 후속 검색어를 만듭니다. 옆으로 쪼개는 게 아니라 아래로 파고듭니다.**

#### 실측 ④ — `reasoning` 스트림이 실제로 옵니다

Search Agent에서는 한 번도 안 왔던 것입니다.

```
**Exploring GraphRAG's Practicality**
I'm focusing on the real-world implementation of GraphRAG…

**Quantifying GraphRAG's Gains**
I'm currently quantifying GraphRAG's improvements, noting a 3.4x accuracy boost…
```

세 가지를 알고 있어야 합니다.

- **영어로 옵니다.** 질문도 답변도 한국어인데 사고 과정만 영어입니다
- **같은 블록이 두 번 출력됐습니다.** 첫 실험에서 다섯 블록이 완전히 똑같이 반복됐습니다
- **실행 로그가 아니라 요약 메모입니다.** 검색으로 가져온 수치를 정리한 것이지, 답을 어떻게 만들었는지의 기록이 아닙니다

#### `data-search-tasks`를 체크리스트 UI로 옮기기

실제 구조입니다.

```json
// 시작할 때
{"tasks":[{"taskId":0, "task":"GraphRAG를 실제 제품에…", "isComplete":false}]}
{"subTaskStatus":"inProgress"}

// 끝났을 때 — 같은 taskId로 다시 옴
{"tasks":[{"taskId":0, "task":"GraphRAG를 실제 제품에…", "isComplete":true,
           "output":{ "references":[…] }}]}
{"subTaskStatus":"complete"}
```

**같은 `taskId`로 이벤트가 두 번 오고 `isComplete`만 `false → true`로 바뀝니다.** 목록을 새로 그릴 필요 없이 체크 표시만 갈아 끼우면 됩니다.

수십 초에서 수 분이 걸리는 API라서, **사용자에게 지금 어디까지 왔는지 보여줄 유일한 수단**이기도 합니다.

#### 규모

| | Search Agent (최대) | DR 1차 | DR 2차 | DR 4차 | DR 5차 | DR 6차 |
|---|---|---|---|---|---|---|
| 하위 과제 | 1개 | 1개 | 1개 | 1개 | 1개 | 1개 |
| 검색 라운드 | 1회 | **2회** | **2회** | 2회 | 4회 | 4회 |
| 검색 쿼리 | 3개 | 10개 | **11개** | 11개 | 23개 | 18개 |
| 출처 | 45개 | 80개 | 139개 | 118개 | **180개** | 132개 |
| 답변 구조 | 평면 3~26섹션 | 4섹션 + 표 | **3부 × 4소섹션** | 표 포함 | 5절 + 표 | 5절 + 표 |
| `reasoning` | 없음 | 5블록 ×2 | 6,418자 | **12,090자** | 8,809자 | 두 번 출력 |
| 검색 소요 | 2.04초 | 3.4초 | 3.41초 + α | — | — | — |

3차는 별도 형식이라 이 표에서 뺐습니다(115출처·3라운드 16쿼리, 아래 3차 절 참고). **출처 수와 답변 품질은 비례하지 않습니다** — 가장 많은 180개를 모은 5차가 근거 품질은 가장 나빴습니다.

**분해는 검색 단계가 아니라 작성 단계에서 일어납니다.** 두 번째 실험 답변은 요청한 세 항목이 그대로 대주제가 되고 각각 소섹션 4개가 붙었습니다.

#### 마크다운 표를 생성합니다

Search Agent 답변에는 표가 없었는데 Deep Research는 만듭니다.

| 검색 유형 | 주요 특징 | 응답 속도 (예상) | 적합한 쿼리 예시 |
|---|---|---|---|
| 벡터 RAG | 텍스트 청크 기반 유사도 검색 | 1~2초 | "A 제품의 가격은 얼마인가요?" |
| 로컬 검색 | 엔티티 및 관계 기반 추론 | 3~5초 | "A와 B 사이의 전략적 관계는?" |
| 글로벌 검색 | 커뮤니티 요약 기반 전역 분석 | 8~15초 이상 | "이 데이터셋의 주요 테마는?" |
| LazyGraphRAG | 동적 검색 및 지연 인덱싱 | 벡터 RAG와 유사 | 실시간 업데이트가 필요한 복잡한 쿼리 |

응답 속도 열은 출처에서 뽑았고, "적합한 쿼리 예시" 열은 모델이 만든 것입니다.

#### 4차 실측 (2026-08-25) — 인용 지시 없이, 문서화가 풍부한 주제로

3. **표 오귀속과 출처 노이즈는 잔존합니다**: 비교 표에 "FSRS-6 — MAE 0.03 미만"이라고 적혔는데 이 수치는 출처상 **다른 모델(GLD-HLR)의 것**입니다 — "무관 실측치를 표에 배치"하는 3차 실측 패턴이 좋은 주제에서도 재현됐습니다. 출처 118개 중 20개가량이 무관 문서(기계가공·산불 연기·화성 탐사·압력 센서·도쿄 에비스 피부과)였으나, 인용이 희박해 본문에 오르지는 않았습니다.

**처음 관측된 실패 유형 — 검색어 발명**: 2라운드 검색어에 `MSR (Massive Spaced Repetition) algorithm research`가 있었는데, **"Massive Spaced Repetition"이라는 약어는 실재하지 않습니다.** 모델이 지어낸 용어이고 그 검색이 Mars Sample Return(화성 시료 회수) 문서를 끌어왔습니다. 즉 동음이의어 오염의 원인은 사용자 쿼리의 어휘만이 아니라 **모델이 검색어 생성 단계에서 스스로 만든 동음이의어**(이번 실행의 `Ebisu`·`FSRs`·`DASH`·발명된 `MSR`)이기도 합니다. 쿼리 어휘를 아무리 다듬어도 이 경로의 오염은 막을 수 없습니다 — 출처 필터링은 결국 소비자 몫입니다.

##### 모델이 스스로 "찾았다"고 판단한 근거입니다

`finish_subtask` 호출의 `reason` 필드가 종료 판단을 그대로 노출합니다.

```
Obsidian Community Surveys 2023-2024), common user sentiments …
```

**구체적인 설문 참조를 찾았다고 판단해서 검색을 멈췄는데, 그 참조가 방금 본 자동 생성 페이지들입니다.** 종료 조건이 "신뢰할 수 있는 근거를 찾았는가"가 아니라 "근거처럼 생긴 문자열을 찾았는가"로 작동합니다.

##### 인용 밀도가 4차와 정반대입니다

**따라서 4차의 종결을 취소합니다.** 인용 밀도를 좌우하는 것이 지시인지, 질문 구조인지, 주제 성격인지 아직 못 가릅니다. §10에 항목을 되돌렸습니다.

| 답변이 쓴 수치 | 출처 대조 |
|---|---|
| MAVEN-ERE 100단어당 8.8개 · ACE 2005 1.8개 · TAC KBP 4.2개 | 출처 원문과 **정확히 일치**. 대상이 셋 다 붙었습니다 |
| Re-TACRED 주석자 평균 일치율 82.3% | **일치** |
| 인과 관계 식별 과제 Fleiss' kappa 0.72 | **일치** |
| TACRED 오류 범주 일치도 κ=0.83 (No Relation 제외 시 0.67) | 숫자는 일치하나 **귀속이 어긋남** — 출처는 TACRED를 사후 재평가한 별도 논문이고, 답변은 "TACRED 데이터셋 구축 과정에서"라고 적었습니다 |
| 섭동 2,400개 · 22유형 · 14개 오픈소스 모델 | 숫자는 일치하나 **어떤 과제인지 안 적음** — 형식 요구를 부분 위반 |
| 카파 0.80 이상이면 학습에 쓸 만하다는 기준 | 출처가 데이터 라벨링 업체 용어집과 마케팅 블로그. **학술 근거 아님** |

**대상이 명확한 수치는 전부 살아남았고, 대상이 흐린 수치에서 위반이 났습니다.** 3차·5차에서 보였던 "완전히 다른 대상의 수치를 표에 배치"하는 극단 사례는 이번에 없었습니다.

##### 결정적 증거 — 걸러진 수치가 있습니다

`finish_subtask`의 `reason`에 종료 판단 근거가 남아 있습니다.

```
specific inter-annotator agreement (IAA) values for key datasets like
TACRED (κ=0.83), Re-TACRED (82.3%), and DocRED (F1=50.7%)
```

앞의 둘은 본문에 그대로 실렸는데 **`DocRED (F1=50.7%)`는 본문에 없습니다.** 수집된 출처 어디에도 이 값이 없고, DocRED 문맥에서 F1이 나오는 대목은 주석자 일치도가 아니라 **모델 성능** 지표입니다.

즉 모델은 판단 단계에서 이미 오귀속을 했고(모델 F1을 주석자 일치도 자리에 놓음), 출력 단계에서 대상을 특정하지 못해 빼 버렸습니다.

**형식 요구는 출력 단계에서 작동하고, 판단 단계에서는 작동하지 않습니다.** 이것이 이번 실험의 답입니다. 오귀속은 지시 위반이라기보다 **정보를 떼어내는 방식 자체의 결과**이고, 형식 요구는 그 결과가 밖으로 나오는 것만 막습니다. 안쪽에서는 계속 일어납니다.

##### 인용 밀도의 갈림 조건이 좁혀졌습니다

| 실측 | 유형 구분 요구 | 본문 인용 |
|---|---|---|
| 4차 | 없음 | 3개 / 118출처 |
| 5차 | **있음** | 조밀 / 180출처 |
| 6차 | 없음 | **1개** / 132출처 |

세 실행 모두 인용 지시가 없었고, 갈린 것은 "출처 유형을 구분해 정리하라"의 유무입니다. **문장마다 어느 유형의 출처인지 밝히게 하면 인용이 따라 붙습니다.** 반대로 그 요구가 없으면 출처를 100개 넘게 모아 놓고도 본문에서는 거의 인용하지 않습니다.

##### Liner 쪽 시스템 프롬프트가 `reasoning`에 새어 나왔습니다

이번 `reasoning` 스트림에는 우리가 준 적 없는 지시를 모델이 자각하는 문장이 여러 개 있었습니다.

| 새어 나온 지시 | 원문 조각 |
|---|---|
| 보고서 마크다운 형식 강제 | `adherence to the "Enhanced Report Markdown Format"` |
| 절당 목표 길이 | `The target length is around 700 words` (절마다 반복) |
| 요약·결론 절 금지 | `avoiding any meta-commentary or summary sections` |
| 엠대시 교체 | `I've also swapped out em dashes with other punctuation` |
| 인용을 마침표 안쪽에 | `ensuring all citations are correctly formatted within periods` |
| 절을 하나씩 처리 | `I will be sure to address it one section at a time as named` |

**답변 길이·절 구성·문장부호가 우리 프롬프트가 아니라 Liner 내부 규칙으로 정해진다는 뜻입니다.** §4-3에서 관측한 "답변 길이 상한"과 §4-4의 "긴 답변은 같은 절이 두세 번 반복된다"가 이 규칙에서 나왔을 가능성이 큽니다. 다만 마지막 절이 "결과적으로 …" 하고 요약 문장으로 끝나므로, **요약 금지 지시는 지켜지지 않았습니다.**

`reasoning`이 같은 내용을 두 번 출력하는 현상(3차 관측)도 재현됐습니다.

##### 예고한 오염은 절반만 나왔습니다

쿼리를 던지기 전에 위험을 두 개 표시해 뒀었습니다.

| 예고한 위험 | 실제 |
|---|---|
| `kappa`가 그리스 문자·유전자명으로 샐 것 | **샜습니다** — 의료 영상 분할 논문(X선 결핵 환자 336명)이 들어옴. 본문 인용은 안 됨 |
| `mutation`으로 축약돼 유전자 문헌이 딸려올 것 | **안 샜습니다** — 섭동 관련 무관 문서(핀란드어 철자 검사기, 시각언어모델)는 들어왔으나 유전학은 없음 |

예고하지 않은 오염도 있었습니다. `partial credit`이 **학생 SQL 과제 채점** 논문을, `triplet matching`이 지식그래프 완성·부분그래프 매칭 같은 다른 하위 분야를 끌어왔습니다.

이번 실행에서 검색어 발명(4차의 `MSR`)은 관측되지 않았습니다. 대신 5차와 같은 **검색어 조이기**가 재현됐습니다 — 라운드가 진행되며 `automated evaluation of relation extraction quality limitations criticism` 같은 평범한 키워드에서 `"DocRED" "inter-annotator agreement" value κ`처럼 따옴표와 그리스 문자까지 검색어에 넣는 형태로 바뀌었습니다.

#### 이번 실험이 드러낸 성질

**출처를 많이 가져오는 것과 정확한 것은 별개입니다.**

`((n))` 인용 번호는 "이 문장이 n번 출처에서 나왔다"가 아니라 **"n번 출처를 참고하는 척한다"에 가깝습니다.** 번호를 클릭해 원문을 대조하기 전에는 신뢰할 수 없습니다.

이 패턴은 단계적으로 심해졌습니다.

```
Search Agent      : 출처에 없는 시간복잡도 수치를 인용 없이 삽입
Deep Research 1차 : "인덱싱 비용"을 "검색 속도"로 바꿔 씀 (인용 번호는 유지)
Deep Research 2차 : 아예 다른 주제의 조사를 끌어다 붙임 (인용 번호는 유지)
Deep Research 5차 : 자동 생성된 페이지의 통계 주장을 1차 근거로 인용 (인용 번호는 유지)
```

**출처가 늘어날수록 위험도 같이 커집니다.**

## 5. Visualization API 와 Visual Answer Agent (실측 완료)

> 초판에서 "한 번도 호출하지 않았다"고 적었던 두 API를 이후 9회 실측했습니다(Visualization 4회, Visual Answer 5회). 이 절은 전부 실측 기준으로 다시 썼습니다.

### 5-1. Visualization API

> **한 줄로**
> 질의를 주면 완결된 HTML 한 장을 만들어 주는 API. 화면 종류(테마)는 자기가 고른다. 준 데이터는 정확히 쓰는데, 안 준 숫자는 지어낸다.

**엔드포인트**: `POST /api/v1/tools/visualization`

두 모드가 있습니다.

**시각화 단독 모드** (자체 검색 엔진을 이미 가진 경우)

| 필드 | 타입 | 필수 | 기본값 |
|---|---|---|---|
| `query` | string | 필수 | 없음 |
| `appearance` | string | 선택 | `"light"` (또는 `"dark"`) |
| `stream` | boolean | 선택 | `true` |

**웹 검색 결합 모드**

| 필드 | 타입 | 필수 | 기본값 |
|---|---|---|---|
| `query` | string | 필수 | 없음 |
| `is_search_context` | boolean | 필수 | 없음. `true`로 두면 웹 검색 근거를 붙임 |
| `date_range` | string | 선택 | `past_day` / `past_week` / `past_month` / `past_year` |
| `max_results` | integer | 선택 | 10 (범위 1~20) |
| `appearance` | string | 선택 | `"light"` |
| `stream` | boolean | 선택 | `true` |

**단가**: 시각화 단독 $10/1,000, 웹 검색 결합 $20/1,000 / 2 QPS

**출력**: `data-atlas` 이벤트 하나에 `atlasArtifact`가 통째로 실려 옵니다.

| 필드 | 설명 |
|---|---|
| `html` | 완결된 HTML 문서 (약 60KB). `iframe`의 `srcdoc`에 그대로 주입 |
| `theme` | atlas가 자동으로 고른 화면 종류 (아래 표) |
| `description` | 모델이 생성한 시각화 설명 |
| `resourceId` | `viz_` 접두사의 고유 식별자 |

#### 테마는 우리가 못 고릅니다 — 관측된 5종

테마 선택은 예시 몇 개를 넣은 별도 분류 호출로 이뤄집니다(`themeInfo.fewShotCount`가 Visual Answer 경로에서 노출됨). 10종 중 5종을 관측했습니다.

| 테마 | 렌더 방식 | 인터랙티브 | 관측 경로 |
|---|---|---|---|
| `comparison` | div 카드 나열 | 아니오 | Visualization, Visual Answer |
| `calculator` | div + 인라인 JS | **예** (입력→계산) | Visualization |
| `process` | div + 인라인 JS | **예** (클릭→상세) | Visual Answer |
| `trend_analysis` | **canvas + Chart.js CDN** | 툴팁만 | Visualization |
| `hierarchy` | div + 인라인 JS 접기 트리 | **예** | Visual Answer |
| `summary` `distribution` `explainer` `game` `instrument` | 미관측 | — | — |

원하는 테마를 지정하는 파라미터는 없지만, **질의를 그 모양으로 쓰면 유도가 됩니다** ("계층 구조로 그려라" → `hierarchy`가 나옴, 1회 성공).

#### HTML의 실체

- **SVG를 쓰지 않습니다.** 9회 연속, `<head>`에 준비된 SVG용 스타일·화살표 마커(`#arrow`)가 한 번도 쓰이지 않았습니다. 매 응답 60KB 중 약 40%가 죽은 코드입니다
- `<head>`에 Liner Prism 디자인 토큰 전체와 보정 스크립트 3종이 실려 오는데, 그 주석에 **사내 이슈 번호(WRI-78/79/80/183)와 한국어 개발 주석이 그대로 노출**됩니다
- `trend_analysis`만 외부 의존이 있습니다: `cdnjs`에서 Chart.js 4.4.1을 로드합니다. **CDN이 차단된 환경·오프라인 임베드에서는 차트가 빈 캔버스로 남습니다.** 또 canvas가 해석 못 하는 CSS 색 함수(`color-mix`)를 쓴 탓에 **범례 색과 막대 색이 어긋나는 실측 사례**가 있습니다
- 폰트·색 토큰을 **지어냅니다.** 존재하지 않는 `var(--font-heading-md-size)`, `var(--color-ring-primary)` 같은 변수를 폴백 없이 씀 — HTML을 낸 8회 중 5회. 무효가 되면 글자 크기·색이 상속값으로 떨어져 강조가 사라집니다

#### 데이터 충실도 — 가장 중요한 성질

| 상황 | 결과 |
|---|---|
| **쿼리에 데이터를 전부 실었을 때** | **정확히 씁니다.** 라벨·수치 완전 일치, 지어낸 값 0. 평균 같은 간단한 파생 계산도 맞은 실측 1회 |
| 값을 안 주고 요청했을 때 | **만들어 냅니다** |
| 웹 검색 결합의 근거 활용 | 6개 항목 중 2개만 검색 근거 사용 |
| 출처 링크를 HTML에 넣어 달라는 요청 | **0개.** 요청해도 안 붙습니다 |
| 쿼리에 함께 쓴 해석("정체 경향") | 검증 없이 그대로 받아 적음 |

**한 화면 안의 숫자 정합성은 보장되지 않습니다.** 표·차트·KPI 카드가 서로 다른 값을 보인 사례가 반복됐고(5회 이상), 본문과 그림이 서로 다른 항목·분류를 담은 사례도 반복됐습니다. 축은 로그 스케일을 쓰지 않습니다 — 1,000배 차이도 선형축에 그립니다.

#### 소요와 스트리밍

- 실측 **10.4~17.4초** (4회 모두). 문서의 "평균 20~30초"보다 빠릅니다
- 스트리밍은 이름뿐입니다. `data-atlas` 이벤트 하나에 HTML이 통째로 옵니다. 진행 표시를 만들 중간 이벤트가 없습니다

#### 파라미터 우회는 안 됩니다

플레이그라운드에서 `appearance` 등을 본문 텍스트에 JSON으로 써 넣어도 **그냥 질의 텍스트로 취급됩니다** (관측된 HTML은 항상 `class="light"`). REST 직접 호출로만 지정할 수 있습니다.

**미확인**: `resourceId`로 이전 결과를 다시 조회하는 엔드포인트가 문서에 없습니다. Visualization 경로에서는 비용·모델 정보(`usage`)가 노출되지 않습니다.

### 5-2. Visual Answer Agent API

> **한 줄로**
> 검색하고, 산문 답변을 쓰고, 그 안에 끼울 그림 한 장까지 만들어 주는 API. 단 질의에 따라 전혀 다른 세 경로 중 하나로 빠지고, 결과물 형태도 그때그때 다르다.

**엔드포인트**: `POST /api/v1/agents/visual-answer`

**입력**: `messages`(필수), `appearance`(`"light"`/`"dark"`), `stream`. `date_range`·`max_results`가 없어 검색 범위를 제어할 수 없습니다.

**단가**: 1,000회당 $150 / 2 QPS

#### 세 경로 — 어떤 질의냐가 결과물의 종류를 정합니다

```
                          ┌─ "그림으로 그려줘" 류  →  ① 이미지 경로
질의 → data-search-decision┤
                          └─ 조사·비교 질의        →  ② 산문 + HTML   또는
                                                     ③ search_web → atlas (도구 경로)
```

| 경로 | 산출물 | 실측 |
|---|---|---|
| ① 이미지 | **PNG 1장 (1024×1024)**, 답변 텍스트 0, 출처 0 | `decision: "image-generation"`, 약 60초. **결과 영역에 렌더되지 않아 SSE 이벤트에서 URL(`api.liner.com/file/image/checksum/…`)을 직접 파내야 했음** |
| ② 산문+HTML | 긴 산문(20절 이상) + `atlasArtifact` | 검색 없이도 검색한 자료처럼 보이는 답변이 나옴 |
| ③ 도구 경로 | 검색 기반 답변 + `atlasArtifact` | Search Agent와 같은 1~2라운드 검색 (7~15쿼리) 후 시각화 |

**같은 $0.15를 내고 무엇이 나올지 예측하기 어렵습니다.** "그려줘"라는 단어가 들어가면 이미지 경로로 빠지는 것이 관측된 유일한 규칙입니다.

#### atlas 엔진 내부가 응답에 노출됩니다

`atlasArtifact`에 문서에 없는 `usage`·`themeInfo`가 붙어 옵니다.

```json
"usage": {
  "model": "gemini-3-flash-preview",
  "costUsd": 0.003617,
  "cacheCreationInputTokens": 0, "cacheReadInputTokens": 0
},
"themeInfo": { "theme": "process", "fewShotCount": 6 }
```

- 시각화 엔진은 **`gemini-3-flash-preview`**
- 시각화 1회 실비 $0.0036~0.0044 — 청구가($0.15) 대비 **34~41배**
- 캐시 미사용(항상 0). 테마 예시(fewShot 6~8개)를 매번 새로 넣음
- 이 비용 유출은 Visual Answer 경로에서만 관측됨 (Visualization 단독에서는 없음)

#### 파싱 요령

- **같은 HTML이 두 번 옵니다.** `data-update`의 `output.html`과 `atlasArtifact.html`이 글자까지 동일 (한 호출에 약 120KB). `usage`가 붙는 **`atlasArtifact` 쪽만 읽으면 됩니다**
- **`atlasInsertionPosition`은 절 인덱스입니다.** 글자·바이트 오프셋이 아니라, 답변을 절 단위로 나눴을 때 몇 번째 절 뒤에 그림을 끼우라는 값 (0=맨 앞, 1=첫 절 뒤)

#### 품질 관측

- 본문 인용이 **지시해도 안 붙습니다** (0~2개). 출처 79~138개가 목록으로만 옴
- **본문과 그림이 서로 다른 항목을 담을 수 있습니다.** 타임라인 실측에서 한쪽에만 있는 항목이 5개였고, 상위 분류를 본문과 그림이 서로 다르게 도출한 사례도 있음
- 날짜를 블로그 게시일로 오인한 사례(출처 3곳이 2024라고 한 것을 2025/03으로 표기), 출처에 없는 이름을 쓴 사례 각 1회
- 긴 답변은 같은 절이 2~3회 반복 출력되고 "답변이 길어져 여기서 마칩니다"로 잘림 — 잘림 안내는 질문 언어를 따라감

## 8. 문서 정오표 — 실제와 다른 곳

직접 던져 보고 확인한 것들입니다.

| 항목 | 문서 | 실제 |
|---|---|---|
| 인용 형식 | `[1]` | **`((2))` 이중 괄호** |
| 후속 질문 필드 | `{ "questions": [...] }` | **`{ "followUpQuestion": { "queries": [...] } }`** |
| `tasks` 필드명 | `id` / `title` / `status` | **`taskId` / `task` / `isComplete`** |
| 하위 과제 상태값 | `pending`, `in_progress`, `completed` | **`inProgress`, `complete`** (`pending`은 미관측) |
| Quick Answer 이벤트 순서 | 출처 → 답변 | **답변 → 출처** |
| Quick Answer 인용 번호 | 붙는다 | **안 붙는다** (2회 모두) |
| Quick Answer `data-search-chunks` | 온다 | **안 온다** (2회 모두) |
| 반복 검색 | 가격 페이지 "반복 검색" / 레퍼런스 "단일 패스" | **질문이 복잡할 때만 반복** |
| `mode` | 가격 페이지 "웹 + 학술" / 레퍼런스 "general 또는 scholar" | **택일. 다만 scholar여도 웹으로 갈 수 있음** |
| `Accept` 헤더 | Deep Research만 필수 | **Quick Answer도 실제로 보냄** |
| Deep Research 400 에러 예시 | `"Field 'query' is required."` | **이 API의 필수 필드는 `messages`** |
| 플레이그라운드 응답 예시 | EV 브랜드 질문에 mRNA 백신 답변 | **고정 샘플. 실행 결과가 아님** |
| Visualization 소요 시간 | 평균 20~30초 | **10.4~17.4초** (4회 실측 전부) |
| Deep Research 하위 과제 | 여러 하위 과제로 분해 | **11회 연속 `tasks` 길이 1 — 분해가 일어나지 않음** |
| 본문 인용이 붙는 경로 | (전 에이전트 공통인 것처럼 서술) | **`mode: scholar`와 Deep Research만. general·Quick Answer·Visual Answer는 인용을 지시해도 안 붙음** (§4-1 매트릭스) |

### UI 라벨과 전송값이 다릅니다

Liner 플레이그라운드는 화면 라벨과 API 값을 일관되게 다르게 씁니다.

| 화면 | 실제 전송값 |
|---|---|
| `Agent` | `"assistant"` |
| `Web Search` | `"general"` |
| `Scholar Search` | `"scholar"` |

코드에 `"agent"`나 `"web"`이라고 쓰면 400이 납니다.

### 화면 검색어와 실제 실행 검색어가 다릅니다

```
화면 Input 표시   : "옵시디언 노션 노트 연결 기능 사용자 통계 조사"
실제 search_query : "옵시디언 노션 노트 연결 기능 사용자 통계 조사 2026"   ← 내부에서 덧붙임
```

각 참조 객체의 `search_query` 필드가 실제 값입니다.

## 9. 구현 시 주의사항

구현 과정에서 확인된 항목을 발생 시점별로 분류하면 다음과 같습니다.

| 언제 걸리나 | 항목 |
|---|---|
| **응답을 파싱할 때** | 날짜 형식이 API마다 다름 · 숫자에 LaTeX 표기가 붙음 · `toolCallId` 길이 가정 금지 · 같은 스트림 안에서 필드 표기가 두 가지 |
| **화면에 뿌릴 때** | `faviconUrl` 직접 사용 금지 · 응답 길이 상한 처리 · 같은 절이 두세 번 반복됨 · atlas HTML 임베드 시 모양 어긋남 |
| **결과를 믿기 전에** | 쓰레기 결과 필터링 · URL 정규화 · **인용 번호를 신뢰하지 말 것** |
| **시각화를 쓸 때만** | `atlasArtifact` 하나만 읽기 |

이 중 인용 번호 항목은 오류가 응답 형식상 드러나지 않으므로 우선 확인이 필요합니다. 나머지 항목은 실행 시 즉시 식별됩니다.

### 날짜 형식이 API마다 다릅니다

```
Web Search    : null           또는  "2026-05-29"
Scholar Search: ""             또는  "2016"  또는  "2016-09-01"
Quick Answer  : ""             또는  "Jun 25, 2024"
```

`new Date("2016")`은 파싱은 되지만 1월 1일로 잡힙니다. 연도만 온 경우를 구분하지 않으면 "2016년 1월 1일 발행"이라고 표시하게 됩니다.

### 숫자마다 LaTeX 표기가 붙습니다 (Deep Research)

```
연평균 성장률(CAGR) \(37.29\%\)      월간 활성 사용자 \(150\)만 명
전년 대비 \(22\%\)                   기존 \(6\%\)에서 \(10\%\)로
```

숫자만이 아닙니다. 5차 실측에서는 **기호도 감쌌습니다** — 위키 링크 문법을 설명하는 자리에서 대괄호가 이렇게 나왔습니다.

```
위키 스타일의 내부 링크(\([]\))를 사용하여 …
```

원래 `[[ ]]`로 적혀야 할 자리인데, 대괄호가 LaTeX 수식으로 감싸지면서 안쪽 내용까지 뭉개졌습니다.

**렌더러가 처리하지 않으면 사용자에게 백슬래시가 그대로 보입니다. 후처리 필수입니다.**

### `toolCallId` 길이를 가정하면 안 됩니다

```
Search Agent      : "call_7b639e91119647f4a65dc027"                       (짧음)
Deep Research 1차 : "call_514163__thought__EucMCuQMARFNMg9rBKKOWDNRy…"    (수천 자)
Deep Research 2차 : "call_463583"                                         (짧음)
```

같은 API인데 사고 서명이 붙기도 하고 안 붙기도 합니다. DB 컬럼이나 로그 키로 쓸 거면 길이 제한에 걸립니다.

`__thought__` 뒤에 붙는 블롭은 base64를 풀어도 해독이 안 됩니다 — 실측 2,360바이트가 protobuf 봉투에 싸인 암호문이었습니다(엔트로피 7.9/8.0, gzip·zlib 아님). 앱이 쓸 수 있는 정보가 아니므로, 저장해야 한다면 `__thought__` 앞에서 잘라 저장하는 편이 안전합니다.

### `faviconUrl`을 화면에 직접 쓰지 마십시오

```
"faviconUrl": "https://www.google.com/s2/favicons?domain=…&sz=128"
```

Liner가 파비콘을 직접 주는 게 아니라 **구글 서비스 URL을 넘겨줍니다.** 그대로 렌더하면 사용자가 어떤 출처를 보는지가 구글로 전송됩니다.

### 쓰레기 결과를 걸러야 합니다

- `hostname`이 `youtube.com`이면 `description`이 댓글 텍스트일 수 있음
- 동음이의어 검색어(`backlinks`, `PKM` 등)는 무관 문서를 대량 끌어옴
- **자동 생성 페이지가 섞여 들어옵니다.** `content` 안에 `[CHART: …]` `[INTERNAL-LINK: …]` 처럼 **렌더링되지 않은 대괄호 자리표시자**가 남아 있으면 사람이 발행한 글이 아닐 가능성이 높습니다 (§4-4 5차 실측). 이 패턴은 정규식으로 걸러낼 수 있으므로, 우리가 `SourceRef` 로 저장하기 전에 검사할 값이 하나 생긴 셈입니다
- 같은 조사 이름이 여러 출처에서 **표본수·연도가 서로 다르게** 인용되면 그 조사는 실재하지 않을 수 있습니다. 사람이 눈으로 볼 때는 잡히는데 답변 본문에 들어가면 안 보입니다
- URL이 `news.ycombinator.com/item?id` 처럼 **쿼리 값이 잘린 채로** 오는 경우가 있습니다 — 열어도 그 글이 아닙니다

### URL 정규화가 필요합니다

http/https 혼재, 경로 대소문자 차이, 검색 쿼리스트링 부착이 확인됐습니다. 같은 문서를 중복으로 세지 않으려면 정규화가 선행되어야 합니다.

### 인용 번호를 신뢰하지 마십시오

**`((n))`이 붙어 있어도 그 문장이 n번 출처와 일치한다는 보장이 없습니다.** 세 단계로 심해지는 패턴이 실측됐습니다.

```
1단계: 출처에 없는 내용을 인용 없이 삽입
2단계: 인용 번호는 유지한 채 출처 내용을 살짝 바꿈 (비용 → 속도)
3단계: 인용 번호는 유지한 채 완전히 다른 주제의 조사를 끌어다 붙임
```

### 응답 길이 상한을 처리해야 합니다

상한에 닿으면 **에러가 아니라 자연어 안내로 끊고 `finish` 이벤트는 정상적으로 나옵니다.**

> "답변이 길어져 여기서 마칩니다. 이어서 보고 싶으시면 계속 써달라고 말씀해 주세요."

응답 구조만 봐서는 완결된 답변과 구분되지 않습니다.

### 긴 답변은 같은 절이 두세 번 반복됩니다

Search Agent·Deep Research·Visual Answer 공통으로, 답변이 길어지면 같은 절이 2~3회 반복 출력됩니다. 반복마다 문구가 조금씩 다르고, **뒤 반복에서 앞 반복에 있던 정보가 빠지는 사례**가 실측됐습니다. "마지막 반복만 취한다"는 단순 규칙은 정보를 잃습니다 — 중복을 정리하려면 반복 구간을 서로 대조해서 합쳐야 합니다.

### atlas HTML은 `atlasArtifact` 하나만 읽으십시오

Visual Answer의 `data-update` 이벤트에는 같은 HTML이 `output.html`과 `atlasArtifact`에 두 벌로 실리고, 그 앞에 누적된 `delta` 조각까지 오갑니다. 전부 받으면 이벤트 하나가 약 120KB입니다. **`atlasArtifact`를 정본으로 삼고 나머지는 버리십시오.** 삽입 위치 `atlasInsertionPosition`은 글자 수가 아니라 **절(문단 블록) 인덱스**입니다 — 0이면 답변 맨 앞, 1이면 첫 절 뒤에 그림을 끼웁니다.

### 같은 스트림 안에서 필드 표기가 두 가지입니다

도구 원출력(참조 문서 목록 등)은 snake_case(`corpus_id`, `search_query`), 최종 참조 이벤트는 camelCase(`referenceChunks`, `referenceId`)입니다. 한 응답 스트림 안에서 두 표기가 섞여 오므로, 파서를 한 규칙으로만 짜면 한쪽을 놓칩니다. 참고로 `corpus_id`는 논문 데이터베이스의 공개 식별자가 아니라 Liner 내부 UUID입니다 — 외부 조회 키로 쓸 수 없습니다.

### atlas HTML을 그대로 임베드하면 모양이 어긋납니다

- 존재하지 않는 CSS 변수(`var(--font-heading-md-size)` 등)를 폴백 없이 쓰는 사례가 잦습니다(§5-1). 앱 쪽에서 폴백 값을 덧씌우지 않으면 글자 크기·색이 상속값으로 떨어집니다
- `trend_analysis` 테마만 Chart.js CDN에 의존합니다 — CDN이 차단된 환경이나 오프라인에서는 차트가 빈 캔버스로 남습니다. 임베드 전에 테마를 보고 분기해야 합니다

## 10. 아직 확인 안 된 것

실측으로 해소된 항목(Visualization·Visual Answer 미호출, `atlasInsertionPosition`의 의미, `data-search-chunks` 구조)은 표에서 뺐습니다. 남은 것과 새로 생긴 빈칸입니다.

| 항목 | 상태 |
|---|---|
| `model` 파라미터의 유효값 | 문서에도 없고 플레이그라운드에도 UI 없음. `modelType`은 빈 문자열로 옴 |
| `lang` 파라미터의 효과 | 안 넣어도 한국어를 자동 인식함. 무엇을 바꾸는지 불명 |
| `authorityScore` | 웹·논문 검색 모두 끝까지 `null` |
| `data-search-step` 이벤트 | 문서에 있는데 전 실측에서 한 번도 안 옴 (Search Agent·Deep Research 포함) |
| 하위 과제 2개 이상이 되는 조건 | Deep Research **11회 연속** `tasks` 길이 1. 6차에서 항목을 다섯 개로 명시했는데도 1개 — 사실상 분해하지 않는 API로 봐야 합니다 |
| 미관측 테마 5종 | `summary` `distribution` `explainer` `game` `instrument` — 어떤 질의가 이를 유도하는지 미확인 |
| 테마별 fewShot 예시 수 | usage 유출로 `comparison`=8, `process`=6만 확인. 나머지 관측 테마 3종은 미확인 |
| `isEssayModeWritingStyleOn`이 켜지는 조건 | `data-search-decision`의 부속 필드로만 관측됨. 어떤 입력이 이를 켜는지 미확인 |
| 전체 소요 시간 / 타임아웃 상한 | 검색 시간만 측정됨. 답변 생성 시간은 데이터에 없음 (Visualization만 §5-1에 총 소요 실측 있음) |
| 답변 길이 상한값 | 잘림 동작만 1회 관측. 몇 자·몇 토큰인지, 고정인지 가변인지 미확인 |
| Deep Research 인용 밀도를 좌우하는 것 | 6차로 후보가 좁혀졌습니다 — "출처 유형을 구분해 정리하라"가 있으면 조밀(5차), 없으면 1~3개(4·6차). 다만 3회 관측이라 다른 요인이 없다고는 못 합니다 |
| Deep Research가 `search_papers`를 쓰는 조건 | 1~3차는 실행, **4·5·6차는 0회**. 6차는 영어 학술 어휘(relation extraction, inter-annotator agreement)를 전면 배치했는데도 웹만 검색함. 어휘 문제가 아니며, 최근 실행에서는 사실상 웹 고정으로 보입니다 |
| `blockedDomains` `forcedSingleSearch` `scholarReferenceFilter` | 응답 메타데이터에 노출된 미공개 필드. REST 요청 파라미터로 넣으면 받아 주는지 미확인 |
| Search Agent 하위 과제 2개 사례 | Q3(근거형)에서 `finish_subtask` 2회 호출 관측. `tasks` 이벤트를 수집 못 해 실제 분해였는지 중복 호출이었는지 미확정 |
| 질의 형태에 따른 Scholar 결과 변화 | 실측은 키워드 질의뿐. 질문형("~의 정의는?")으로 던지면 다른 성격의 논문이 오는지 미확인 — §3-2의 "Web이 낫다" 판단은 키워드 기준 한정 |
| Search API 페이지네이션 | `max_results` 상한 20이 전부. 오프셋 파라미터 없음 |
| 공식 SDK | 존재 여부에 대한 언급 없음. 예제는 curl / TypeScript / Python 조각뿐 |
| 데이터 보관·학습 활용 정책 | 개발자 문서 본문에 없음. 별도 API 이용약관 문서로 링크만 |
| `X-RateLimit-*` 헤더 | `Retry-After`만 언급됨 |

### 문서 간 불일치 (미해결)

quick-start 페이지는 응답이 `choices[].delta.content`로 온다고 적었는데, Agent API 레퍼런스는 모두 `text-delta.delta`라고 적습니다. 실측에서는 `text-delta`가 왔습니다.

## 11. Liner의 자리 — 모델이 아니라 완성 서비스

§1~§10은 Liner가 무엇을 주는지를 적었다. 이 절은 **그것이 우리 앱의 어느 자리에 놓이는가**를 적는다. 결론부터 적으면, Liner는 대화를 지휘하는 주체가 될 수 없다.

### 11.1 두 층을 가르는 선

우리가 "AI API"라고 부르는 것에는 성격이 다른 두 층이 섞여 있다.

| 층 | 예 | 파는 것 |
|---|---|---|
| 모델 API | Gemini API, Anthropic API | **모델을 골라 쓰는 권한.** 토큰당 과금 |
| 에이전트 서비스 | **Liner** | **완성된 작업.** 호출당 정액 |

Gemini는 뇌를 빌려준다 — 도구는 우리가 쥐어주고 루프도 우리가 돈다. Liner는 이미 도구를 쥔 뇌이고, 자기 루프를 돌아 결과만 준다.

### 11.2 근거 — 전부 실측

| 근거 | 확인한 곳 |
|---|---|
| **`tools` 파라미터가 없다** | §4-2 · §4-3 입력 표. 7종 전부 확인. `tools/`는 URL 경로(`/api/v1/tools/search/web`)에만 나오며 자기 엔드포인트 분류다 |
| **`system` 역할이 없다** | §4-1. `role`은 `user`·`assistant`뿐이라 규칙을 고정할 자리가 없다 |
| **지시가 검색 단계에 닿지 않는다** | §4-1 「프롬프트 지시문의 실제 효과」. 검색 범위 제한이 검색어에 전달되지 않았고 제외 연산자는 0회였다. **다만 맥락은 검색어 재작성까지 전달된다** |
| **출력 형식 지시는 무시되기 쉽다** | 같은 표. 판정 라벨·문장 단위 인용 번호가 무시된 사례 |
| **`model` 유효값이 비공개다** | §4-3 · §10. Quick Answer는 `mode`도 `model`도 없어 모델 선택 자체가 불가능하다 |
| **재현성 보장이 없다** | §4-2. "같은 질문을 나중에 다시 던졌을 때 같은 답이 나온다는 보장이 없다" |
| **호출당 정액 과금** | §2 과금. 토큰 단위가 아니다 |
| **MCP가 자기 도구 5종을 노출한다** | §6. `search_web` 외 4종. 지휘자가 아니라 부품으로 쓰이도록 설계됐다 |

Liner가 내부적으로 부르는 도구는 `search_web` · `search_papers` · `search_paper_sections` · `update_search_status` · `finish_subtask` 이며 전부 내장이다. 우리 도구를 끼워 넣을 구멍이 없다.

> 시각화 엔진 atlas 가 `gemini-3-flash-preview` 로 구동된다는 관측(§0)은 **Visualization API 에 한한 것**이다. 나머지 6종의 내부 모델은 확인된 바 없으므로 위 근거에 포함하지 않는다.

### 11.3 결합 방향은 하나뿐이다

```text
✗  Liner 에게 우리 도구를 쥐어준다         tools 파라미터가 없다
✓  우리 모델에게 Liner 를 도구로 쥐어준다   MCP 또는 REST
```

이는 [ADR-0009](../adr/0009-llm-provider-gemini.md) §3의 배치와 일치한다. Liner는 처음부터 feature 3(정보 간극 메우기 · fact-check)의 **출처 검색** 담당이었고, 이번 실측은 그 배치가 옳았음을 확인한다.

공식 MCP 문서가 이 방향을 명시한다.

> Clients (like Claude Desktop, Cursor, VS Code) connect to Liner's remote MCP server to access Liner's tools. **The client consumes Liner's capabilities rather than registering its own tools with Liner.**
>
> — [liner.com/ko/developers/docs/mcp](https://liner.com/ko/developers/docs/mcp) (2026-08-25 확인)

MCP 라는 이름이 양방향처럼 들리지만 한 방향이다. 서버가 도구를 내놓고 클라이언트가 가져다 쓴다. Liner 가 서버이고 우리가 클라이언트다.

엔드포인트는 `https://platform.liner.com/api/v1/mcp`(Streamable HTTP)이며, 인증은 브라우저 환경의 OAuth 2.1 또는 헤드리스·CI 용 `Authorization: Bearer $LINER_API_KEY` 다.

```bash
# Claude Code 에 붙일 때 (헤드리스·API 키)
claude mcp add --transport http liner https://platform.liner.com/api/v1/mcp \
  --header "Authorization: Bearer $LINER_API_KEY"
```

**다만 우리 앱은 MCP 클라이언트가 아니다.** Tauri 웹뷰에서 MCP 를 쓰려면 클라이언트를 따로 구현해야 하므로, 앱 안에서는 REST 직접 호출이 현실적이다. MCP 는 Claude Code · Cursor 같은 기존 호스트에서 같은 도구를 미리 시험해 볼 때 쓴다.

MCP 제공 여부가 여기서 갈린다(§6).

| API | MCP |
|---|---|
| Search · Scholar · Quick Answer · Search Agent · Deep Research | 제공 |
| Visualization · Visual Answer | **미제공 — REST 로 직접 호출해야 한다** |

### 11.4 우리 코드에 미치는 영향

Liner를 대화 주체로 놓으면 다음이 무효화되거나 불안정해진다.

| 대상 | 상태 | 이유 |
|---|---|---|
| `queryTools.ts` 의 도구 4개 전부 | **무효** | 주입 경로가 없다 |
| `queryAgent.ts` SYSTEM 중 "도구로 위키를 찾아 읽어라" | **무효** | 같은 이유 |
| SYSTEM 중 "같은 개념의 다른 이름도 떠올려 찾아봐라" | **무효** | 지시가 검색 단계에 안 닿는다 |
| SYSTEM 중 `[추론]` 라벨 규칙 두 줄 | **불안정** | 출력 형식 지시는 무시되기 쉽다. 항상 무시되는 것은 아니다 |

즉 [wiki-qa-agent.md](wiki-qa-agent.md) §11.5가 프롬프트로 세워 둔 근거 구분이 **코드로 다시 구현되어야** 성립한다.

그리고 Liner는 검색을 끌 수 없다(§4-2 — Quick Answer는 항상 웹 검색만 한다). 위키에 답이 있어도 웹을 보고, 매번 과금되며, 필기 일부가 매번 밖으로 나간다.

### 11.5 남는 질문

Liner가 뇌 자리에 앉을 수 없다면 **그 자리를 무엇이 맡을 것인가**가 남는다. 이 문서의 범위를 벗어나므로 여기서는 질문만 기록한다.
