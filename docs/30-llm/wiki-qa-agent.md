# Wiki QA Agent (질의 계층)

내 지식 지도에 **질문하고 근거와 함께 답받는** 에이전트. PiecePool의 빠진 "읽기(query)" 절반.

> **상태**: §1~§10 은 제안이다. 그중 일부를 **PIE-76 쿼리바**로 구현 중이다 — 실제로 만든 것,
> 정한 값과 그 근거, 제안과 어긋나는 부분은 **§11** 에 적는다.
> 원래 메모: MVP scope([`../00-overview/scope-mvp.md`](../00-overview/scope-mvp.md))엔 없음 — 신규 기능 → 이슈로 추적 후 도입.
> 외부 영감: research-wiki-skill-kit (vault → 에이전트, 근거 분리, 환각 가드).
> 근거 분리 규칙은 [`prompt-templates.md`](prompt-templates.md) §6과 SSOT 공유.

---

## 1. 동기

현재 PiecePool은 archive → wiki/relations를 **생성(write)**만 한다. 만들어진 위키·그래프에 **질문할 방법이 없다**. skill-kit이 정확히 이 빈칸: vault를 탐색해 출처 인용과 함께 답하는 에이전트.

핵심 차별: 일반 챗봇과 달리 **반드시 사용자 vault 파일에 근거**한다. 모르면 지어내지 않고 "근거 없음"을 반환한다.

---

## 2. 입력 (vault 경로)

[`../10-contracts/workspace-layout.md`](../10-contracts/workspace-layout.md) 구조를 읽기 전용으로 탐색.

| 경로 | 노트 타입 | 역할 |
|---|---|---|
| `<space>/wiki/*.md` | WikiPage | LLM 정리본 (1차 답변 출처) |
| `<space>/archive/*.md` | ArchiveNote | 사용자 원문 (근거 확정) |
| `<space>/relations/relations.json` | Relation | 개념 간 타입 관계 (탐색 확장) |
| `<space>/sources/original-files/*` | Source 원본 | PDF/이미지 인용 |

엔티티 정의: [`../10-contracts/entities.md`](../10-contracts/entities.md).

---

## 3. 검색 순서 (노트 타입 구분 — skill-kit 흡수)

질문 → 다음 순서로 좁힌다. **정리본(wiki)에서 시작해 원문(archive)으로 근거를 확정**한다.

```text
1. wiki/         제목·summary·aliases·frontmatter 매칭 → 후보 WikiPage
2. relations     후보 개념의 part_of/used_in/confused_with 등으로 이웃 확장
3. archive/      WikiPage.sourceIds → 원문에서 실제 근거 문장 확인
4. sources/      필요 시 PDF page/이미지 인용 ([[file#page=N]])
```

- WikiPage(정리본)와 ArchiveNote(원문)를 **섞지 않는다**. 답은 정리본 기반, 근거는 원문 기반.
- relations로 "헷갈리는 개념"(`confused_with`), "선행 개념"(`prerequisite`)을 자동 동반 제시.

---

## 4. 응답 규칙 + 인용 형식

```text
[응답 규칙]
- 모든 사실 주장 뒤에 출처를 단다.
- 출처는 WikiPage title 또는 원본 파일(SourceRef/Evidence) 단위.
- 저장된 노트 내용 vs 너의 추론을 라벨로 구분한다.
  · "[원문]" = archive/source 근거 있음
  · "[정리]" = wiki 정리본 기반
  · "[추론]" = 근거 없이 보충 (남용 금지, 명시 필수)
- 근거를 못 찾으면 "근거 없음 — vault에 관련 내용이 없습니다"를 반환한다.
```

인용 표기는 기존 모델 재사용(신규 타입 정의 안 함):

- 파일/페이지: `[[transformer-week3.pdf#page=12]]` ([`../10-contracts/wikilink-embed.md`](../10-contracts/wikilink-embed.md))
- 구조화 근거: `SourceRef` / `Evidence`([`../10-contracts/entities.md#sourceref`](../10-contracts/entities.md#sourceref), [`#evidence`](../10-contracts/entities.md#evidence)) — `quote`/`reason`/`page` 그대로 사용.

## 5. Grounding Guard (idea ② 상세)

저장형 앱이라 환각이 곧 신뢰 붕괴. 4중 가드:

| 가드 | 규칙 | 위반 시 |
|---|---|---|
| **무근거 차단** | 모든 주장에 wiki/archive/source 근거 1개 이상 | "근거 없음" 반환 |
| **추론 격리** | 일반지식 보충은 `[추론]` 라벨 강제 | 라벨 없으면 답변 거부 |
| **원문 우선** | wiki 정리본과 archive 원문 충돌 시 원문 채택 + 충돌 표시 | 자동 수정 금지(사용자에 표시) |
| **경로 검증** | 인용 파일·page가 실존하는지 확인 | 깨진 인용 표시, 답에서 제외 |

> 마지막 두 규칙은 [`../10-contracts/wikilink-embed.md`](../10-contracts/wikilink-embed.md) "자동 삭제·덮어쓰기 금지" 원칙과 정렬.

## 8. 에이전트 Eval (idea ④ — 자동 테스트 질문)

skill-kit "난이도별 질문 10개로 검증"을 PiecePool eval에 흡수. **seed vault**(AI/OS/자료구조, [`../00-overview/scope-mvp.md`](../00-overview/scope-mvp.md) §2.9)로 회귀 테스트.

### 8.1 테스트 질문 자동 생성

각 WikiPage에서 난이도별 질문 파생:

| 난이도 | 패턴 | 정답 파일 |
|---|---|---|
| easy | "X가 뭐야?" (단일 개념 정의) | 해당 WikiPage |
| medium | "X와 Y 차이?" (`confused_with`/`contrasts`) | 두 WikiPage + relation |
| hard | "X는 어디에 쓰여?" (cross-subject `used_in`) | 다중 space WikiPage |
| trap | vault에 없는 개념 질문 | **"근거 없음" 반환해야 통과** |

### 8.2 통과 기준 (skill-kit QA 리뷰 축)

| 축 | 통과 |
|---|---|
| **파일 attribution** | 답이 정답 WikiPage/Source를 실제로 인용 |
| **환각 0** | trap 질문에 지어내지 않고 "근거 없음" |
| **추론 격리** | `[추론]` 라벨 없는 무근거 주장 0 |
| **경로 유효** | 인용한 파일·page 모두 실존 |

### 8.3 실행

[`evals.md`](evals.md) 하니스 확장: `npm run eval -- --agent --space <slug>`. 결과는 import eval과 같은 results/ 비교 표 형식.

## 11. 구현 — PIE-76 쿼리바

§1~§10 은 제안이다. 여기는 실제로 만든 것과 정한 값을 적는다.

설계 전문은 Linear 문서 "쿼리바 설계". 코드는 `src/llm/queryAgent.ts`(주고받기 루프) ·
`src/llm/queryTools.ts`(도구 정의와 실행) · `src/lib/wikiInsert.ts`(위키 반영).

### 11.1 검색 방식 — 앱이 좁히지 않고 AI 가 찾는다

§3 은 앱이 순서대로 좁혀 들어가는 방식이다. 실제로는 **AI 에게 읽기 전용 도구를 쥐어주고 스스로
찾게** 한다. 위키가 늘어나면 앱이 미리 다 넣어 줄 수 없기 때문이다.

| 도구 | §3 의 어느 단계인가 |
|---|---|
| `list_spaces` · `list_wiki` | 1. wiki 후보 찾기 |
| `read_wiki` | 1. 정리본 읽기 |
| `get_relations` | 2. 이웃 확장 |
| — | 3. archive 원문 · 4. sources 인용 — **아직 도구가 없다** |

네 도구 모두 읽기 전용이라 실행 전 사용자 확인이 필요 없다.

### 11.2 상한 — 얼마이고 왜 그 값인가

| 값 | 얼마 | 근거 |
|---|---|---|
| 주고받기 상한 | **6회** (`MAX_ROUNDS`) | 무한 반복 방지이자 **비용 상한**이다. 매 회차마다 지금까지 오간 내용 전체를 다시 보내므로 횟수가 곧 돈이다. 착수 전 실측(스파이크)에서는 3회로 끝났다 |
| 위키 본문 인라인 상한 | **6,000자** (`WIKI_INLINE_LIMIT`) | 가장 큰 호출을 2만 자 이하로 두는 것이 목표다. 고정비(도구 설명서 1,000 + 질문 500 + 위키 목록 1,700 ≈ 3,200자)를 빼면 약 1만 6천 자가 남고, AI 는 보통 위키를 두세 개 읽으므로 하나당 5,600~8,400자다. 여유를 두고 6,000 으로 잡았다. **시작값이며 실측 후 조정한다** |
| 목록 요약 길이 | 80자 (`SUMMARY_LIMIT`) | 위키 목록 한 줄이 길어지면 고정비가 불어난다 |
| 모델 | `gemini-3.1-flash-lite` (`GEMINI_QUERY_MODEL`) | **하루 요청 한도** 때문이다. `gemini-3.5-flash` 는 무료 티어 RPD 가 20회라 대화 몇 번이면 소진된다. 쿼리바는 한 질문에 도구 왕복이 여러 번 붙어 특히 빨리 닳는다 |

상한을 넘긴 본문은 자르지 않고 **소제목 목록 + 앞부분**만 돌려주며, AI 가 `section` 인자로
필요한 소제목을 지정해 다시 부른다. 그 안내는 사람이 아니라 AI 가 읽는다.

### 11.3 재시도 — provider-config §4.1 과 다른 점

쿼리바 루프는 provider 어댑터가 아니라 별도 호출 경로다. 재시도 규칙도 여기서 따로 정한다.

| 응답 | 동작 | 왜 |
|---|---|---|
| 429 · 5xx | 재시도 최대 **2회**, 500ms 지수 backoff | 잠깐 몰린 것이라 기다리면 풀린다 |
| 네트워크 오류 | 재시도 최대 **2회** | 일시적 끊김 |
| 401 · 400 | **즉시 던진다** | 키나 요청이 잘못된 것이라 다시 해도 같은 답이다 |
| 중단(`AbortError`) | **즉시 던진다** | 창이 닫힌 것이라 재시도할 대상이 없다 |

[`provider-config.md`](provider-config.md) §4.1 과 두 군데가 다르다. 응답 헤더 `Retry-After` 를
아직 존중하지 않고, 429 를 1회가 아니라 2회까지 재시도한다. 어댑터 경로를 바꾸지는 않았다.

도구 실행(`runTool`)은 **어떤 경우에도 예외를 던지지 않는다.** 없는 폴더·파일·소제목이든 IPC
실패든 전부 문자열로 돌려준다 — 주고받기 도중 예외가 나면 대화 전체가 끊기지만, 문자열로 주면
AI 가 스스로 다른 것을 찾는다.

### 11.4 제안과 다르게 간 것 · 아직 안 한 것

| 제안 | 지금 상태 |
|---|---|
| §3 archive 원문 · sources 인용 | **없다.** 위키 정리본까지만 읽는다 |
| §4 `[원문]` / `[정리]` / `[추론]` 라벨 | **`[추론]` 만 쓴다.** 안 붙은 문장은 위키에서 온 것이라는 규칙을 함께 두어, 모든 문장에 라벨을 다는 것과 같은 구분을 하면서 글이 안 지저분해진다. `[원문]` 은 archive 도구가 없어 아직 쓸 수 없다 |
| §5 Grounding Guard 4중 | **무근거 차단을 완화했다** — 아래 11.5. 나머지 셋(추론 격리·원문 우선·경로 검증) 중 추론 격리만 라벨로 두었고 기계 검증은 없다 |
| §6 모호 질문 되묻기 | **없다** |
| §7 근거 목록 · 관련 개념 블록 | **뒤집었다.** 참고한 파일 목록을 따로 띄우지 않고 답변 글 안에 위키 제목만 남긴다 (PIE-76 결정) |
| §8 에이전트 Eval | **없다** |

§5 는 본 문서 §10 이 "우선순위 최상"이라고 적어 둔 항목이다. 지금은 프롬프트 지시뿐이므로,
저장형 신뢰가 걸린 만큼 후속으로 다시 봐야 한다.

### 11.5 §5 무근거 차단을 완화한 이유

§5 는 근거를 못 찾으면 "근거 없음"을 반환하라고 정했다. 저장형 앱에서 환각이 신뢰를 무너뜨리기
때문이고, §10 이 이 항목을 우선순위 최상으로 꼽은 것도 그래서다.

그런데 실측에서 이 규칙이 앱을 못 쓰게 만들었다. 사용자가 "FP, FN, TP, TN 이 뭐야" 라고 물었는데
위키에는 `type-i-error.md` · `type-ii-error.md` 로 내용이 **분명히 있었다.** 다만 본문이 "귀무가설이
참인데도 기각하는 오류" 라고 적혀 있어 **FP · false positive · 위양성이 한 글자도 없었다.** 근거를
못 찾은 것으로 판정돼 "모른다" 가 나왔다.

같은 개념을 부르는 말이 사용자와 위키에서 다른 것은 흔한 일이다. 그때마다 "모른다" 를 반환하면
비서로 쓸 수가 없다.

그래서 **차단 대신 구분**으로 바꿨다.

| 상황 | 동작 |
|---|---|
| 위키에서 찾음 | 그 내용으로 답하고 위키 제목을 문장에 적는다. 라벨 없음 |
| 위키에서 못 찾은 부분을 보충 | 그 부분 앞에 `[추론]` |
| 위키에 아예 없음 | 첫 줄에 그 사실을 밝히고 그다음부터 `[추론]`. **답을 거부하지 않는다** |

`[추론]` 이 안 붙은 문장은 반드시 위키에서 온 것이라는 규칙을 함께 둔다. 이 규칙이 있어야 라벨이
뜻을 갖는다 — 없으면 "라벨이 안 붙었다" 가 아무것도 보장하지 않는다.

환각 위험을 없앤 것이 아니라 **보이게** 만든 것이다. §5 의 나머지 세 가드(추론 격리·원문 우선·
경로 검증)는 여전히 후속 과제다.

### 11.6 위키에 넣자는 제안은 하지 않는다

대화 중에 "이거 위키에 추가할까요?" 를 띄우지 않는다. 프롬프트로도 금지한다.

위키는 형식(제목·요약·예시·근거 등)이 어느 정도 채워져야 만들어지는 문서다. 대화 도중 즉석으로
만들면 **형식이 반쯤 빈 문서**가 생기고, 그게 쌓이면 위키 전체의 신뢰가 떨어진다.

`/lint` 는 **이미 있는 위키를 채우는** 일만 한다. 새 위키 파일은 만들지 않는다.

> **후속** — 위키의 구조(형태)가 확정된 뒤에, `/lint` 로 그 구조에 맞춰 위키 내용을 채우는 흐름을
> 만든다. 새 위키를 언제 어떤 조건에서 만들지도 그때 함께 정한다.
